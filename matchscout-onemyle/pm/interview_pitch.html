The killer sentence (use for most interviews)

Pre-rehearsed — say word-for-word the first time
"I built a recommender system for a B2B creator marketplace. It's a two-stage retrieval pipeline with an LLM re-ranker on top, and I held out 10% of gigs as a no-LLM control to measure whether the LLM was actually moving outcome metrics."

Why this sentence works

  • Sounds humble — "recommender system" is familiar territory
  • Demonstrates rigor — "held out a control" signals real engineering discipline
  • Implies sophistication without name-dropping — "LLM re-ranker" is a clean technical term
  • Invites the right follow-ups — interviewer pulls on whichever thread they care about
  • You let depth come out through questions, not by pushing it on them

Layered narrative — simple at the top, deep when probed

Layer 1 — One sentence (busy hiring manager, recruiter screening)
"I built a recommender system that suggests 3 creators when a business posts a job in a creator marketplace."
Layer 2 — 30 seconds (curious recruiter, casual mention)
"It's a two-stage retrieval pipeline — rules-based filtering followed by sentence-transformer cosine ranking — that narrows the catalog to 10 candidates. Then a Claude-based LLM picks the final 3 with reasoning. I held out 10% of gigs as a no-LLM control so I could causally measure whether the LLM was actually adding value over plain cosine ranking."
Layer 3 — 2 minutes (technical interview, hiring manager who's engaged)
"Three stages: hard filter on location / budget / content-type → sentence-transformer cosine over a rich embedding that includes profile bios + categories → LLM re-ranker for 90% of gigs. The other 10% are a no-LLM control that just takes the top 3 by cosine — that's the baseline I measure against. The LLM reasons over each candidate's recent gig history and per-metric ranks within the top-10 set, using a versioned prompt template. Outcome dashboard segments by treatment arm AND prompt version, with chi-squared significance, so prompt iteration is empirically driven against real outcomes. Pre-deploy eval is just a pytest schema smoke test — no synthetic golden set, because golden sets on synthetic data don't predict production outcomes. Ragas, DeepEval, Promptfoo are dev-time tools I use during prompt iteration, not CI gates."

Robustness Q&A — likely tough questions, prepared answers

Q: "How do you know the LLM is actually helping?"
"That's exactly what the A/B measures. 10% of gigs go to a no-LLM control — top 3 by cosine score. The other 90% go through the LLM. We compare acceptance rate, top-1 selection rate, and gig success rate per arm, with chi-squared significance. If the LLM arm doesn't beat the control, we know it isn't earning its cost — and we'd shrink Arm 2 or iterate the prompt."
Q: "Why not just use cosine similarity / why bother with the LLM?"
"Honestly, on synthetic structured data, a hand-tuned scoring function might do most of what the LLM does. The LLM earns its place by reasoning over relational history that cosine can't see — 'this creator has 8 successful gigs and only 1 failed in this category' or 'this candidate has high followers but a poor reliability track record.' That's structured reasoning over multiple signals, not vibe matching. The A/B is exactly how we verify whether it's worth the cost."
Q: "Why don't you have a pre-deploy eval / golden set?"
"Deliberate choice. Synthetic golden sets on synthetic data are intellectually satisfying but they don't predict production outcomes — they grade your own homework. Outcome A/B against a no-LLM control is what mature production teams use (Airbnb, DoorDash, Etsy), and I followed that pattern. CI runs only a pytest schema smoke test — catches broken code, not bad LLM output. The actual quality eval is the outcome dashboard, segmented by treatment arm and prompt version."
Q: "What's the cold-start problem and how did you handle it?"
"When a new creator or business has no past gigs, the LLM's history-based reasoning has less to work with. I handle it implicitly — profile descriptions are stored fields on every creator and business (written at signup, like an Instagram bio). They're part of Stage 2's embedding text and part of the LLM's context. When a candidate has sparse past-gig data, the LLM marks reliability_estimate as 'low' and weighs profile alignment more heavily. No separate cold-start arm — that was a design I considered and rejected because it complicates the experiment without buying much."
Q: "How do you guard against LLM hallucination?"
"Three layers. First, Pydantic schema validation inline — runtime guard against malformed output. Second, the outcome dashboard catches degradation post-hoc: if acceptance rate drops, that's the signal that prompt or LLM behavior changed. Third, during prompt iteration, I use Ragas faithfulness on a sample of recent outputs to confirm grounding, and DeepEval assertions to check that cited past gigs actually exist in the database. These are dev-time tools, not CI gates."
Q: "How does prompt iteration actually work?"
"The prompt is a versioned template file — prompts/arm2_v1.txt. When I want to iterate, I copy it to arm2_v2.txt, edit, bump PROMPT_VERSION, deploy. Every recommendation row stamps which prompt version produced it. The outcome dashboard segments metrics by (treatment_arm, prompt_version), so I can causally measure v1 vs v2 on real outcomes. Promptfoo helps me preview a new prompt against recent gigs side-by-side with the current one before deploying. Iteration loop is: deploy → measure → diagnose with traces → edit prompt → bump version → measure again."
Q: "What's the cost?"
"$0 for Arm 1 (no LLM). About $0.30 per gig for Arm 2. At marketplace scale that's a real operating cost, which is why the control arm matters — if the LLM isn't lifting outcomes enough to justify $0.30/gig, we'd shrink Arm 2 and lean on cosine ranking. V2 brings that cost down — see the V2 roadmap section below."
Q: "What's the biggest weakness?"
"Statistical power. With a small PoC dataset, the A/B doesn't reach significance — results are directional, not conclusive. Production validation needs N ≥ 100 per arm over weeks. We're honest about that in the PRD. Also: the synthetic data limits how well outcome metrics generalize. The methodology is solid; the numbers will be more meaningful once real Onemyle data flows through it."
Q: "Why Claude over GPT-4 / Gemini?"
"Claude Sonnet 4.6 hit the cost-quality point we needed. The architecture abstracts the LLM call behind a single function, so swapping providers is a 10-line change. For V2, multi-cloud routing (Bedrock primary, OpenAI fallback) is on the roadmap."
Q: "Is this in production at Onemyle?"
"It's a PoC validated on synthetic data — productionization is pending Onemyle's roadmap prioritization. I lead the initiative as their Pro Bono Product/AI Lead and Investor. The full design docs, dashboard, and PM artifacts are real and complete; what's pending is the integration with their live data."

V2 roadmap — memory layer + Agent SDK subagents

Why this section exists
V2 has two coherent engineering investigations, both pinned to MatchScout's actual V1 limitations:
  • Memory layer (Zep / Mem0 / Anthropic Memory tool / Letta benchmarked) — solves V1's context bloat. Compresses raw history into compact priors.
  • Agent SDK subagent rebuild of Stage 3 — solves V1's hallucination risk + adds self-improvement. Decomposes the single LLM call into specialized subagents.
They're multiplicative: memory compresses data, subagents distribute work. Each subagent reads only its compact memory slice.

The V1 inefficiency (stated plainly)

Every Arm 2 recommendation in V1 re-loads the same raw data and re-reasons from scratch:

Input to Stage 3 per gig (Arm 2):
  - Gig brief                                       ~  200 tokens
  - 10 candidate profiles (full)                    ~1,500 tokens
  - 10 candidates × up to 10 past gigs each         ~3,000 tokens
  - Per-metric ranks within the 10                  ~  200 tokens
  ─────────────────────────────────────────────────
  Total                                             ~5,000 tokens

~5K input tokens per gig forever. And the LLM keeps re-discovering things it should already know.

Prepared interview answers — when V2 / memory comes up

Q: "How would you optimize MatchScout V1?"
"The biggest inefficiency is that V1 re-feeds raw past-gig history on every recommendation — about 5,000 input tokens per gig, most of which is the same history the system has seen before. V2 introduces a memory layer that distills history into compact priors: per-business preferences, per-creator personas, cross-gig patterns, and reflexion-style self-critiques. The LLM reads compact memory snippets instead of raw rows. Result: ~78% reduction in input tokens, ~73% LLM-cost reduction, ~50% latency reduction. Plus a fraction of gigs can skip the LLM entirely when memory consensus is high-confidence."
Q: "Which memory framework would you use for V2?"
"Depends on the workload. I benchmarked four — Zep, Mem0, Anthropic's native Memory tool, and Letta — on MatchScout's actual memory workload. Short version: Mem0 for semantic facts (business preferences as text), Zep for temporal/episodic queries (when did biz_042 last reject a creator and why), Anthropic Memory tool when you want minimal infra and the system is Claude-native, Letta when business histories become very long (multi-year accumulation). For MatchScout V2 specifically, I'd lean Mem0 + Anthropic Memory tool combined — Mem0 for distilled preferences, Anthropic's tool for conversational continuity within a recommendation cycle."
Q: "How does the memory get updated?"
"Async, after each gig completes. The pipeline doesn't wait. When outcome is known (business picked a creator, gig succeeded or failed, ratings collected), a small post-processing job updates business memory ('biz_042 picked creator_X over Y on a $700 budget; succeeded'), creator memory ('creator_X: +1 success in food_beverage'), and feeds the LLM's self-critique into reflexion memory. The next recommendation reads the updated state. Recommendation latency is unaffected."

Why memory + subagents work multiplicatively

Memory makes subagents affordable. Subagents make memory access targeted. Without memory, decomposing into 5 subagents would each load thousands of tokens of redundant raw history → cost balloons. With memory, each subagent gets only its compact slice (~400 tokens), making decomposition tractable.

Prepared interview answers — when Agent SDK / subagents come up

Q: "Have you used Claude Agent SDK?"
"Yes — I designed MatchScout V2's Stage 3 on it. V1 uses a single LangGraph LLM call inside Stage 3 Arm 2. V2 decomposes that into specialized subagents — history/context, reasoner, fact-checker, and a Reflexion critic — using the Agent SDK's subagent primitives. The fact-checker subagent is the headline feature: it validates the reasoner's cited past_gigs against the database BEFORE the recommendation emits, catching hallucinations inline instead of post-hoc. The Reflexion critic writes self-critiques into memory across gigs, so the agent learns from its own past mistakes."
Q: "Why use the Agent SDK if LangGraph already works?"
"Different tools, different sweet spots. LangGraph is right for V1 — explicit state machine, one LLM call, vendor neutrality. V2 isn't replacing LangGraph wholesale; just swapping the internals of the Stage 3 node. The Agent SDK earns its place when you want native subagent patterns, Anthropic Memory tool integration, and Reflexion loops without hand-rolling them. LangGraph stays for the higher-level pipeline orchestration; Agent SDK runs inside the Stage 3 node."
Q: "Doesn't a 5-subagent decomposition cost more than one LLM call?"
"It would, if memory weren't compressing the data. Five subagents each loading 5K tokens of raw history is 25K tokens total — much more than V1. But with the memory layer compressing inputs to ~400 tokens per subagent slice, the total is around 2K tokens across 5 calls — comparable to V1's single 5K-token call. So memory and subagents are multiplicative: memory makes the decomposition affordable, subagents make the memory access targeted. Net cost is similar to V1; the win is quality (inline fact-check, Reflexion, personalization)."
Q: "Why the fact-checker subagent specifically?"
"Hallucination in MatchScout would mean the recommender citing a past gig that doesn't exist — e.g., 'creator_042 had 8 successful gigs at this business' when the DB shows 2. In V1 I catch that post-hoc via Ragas faithfulness during dev-time iteration. The fact-checker subagent catches it INLINE — it sees what the reasoner cited and validates each claim against the database before the recommendation emits. That's a real product win: hallucinations never reach the business in V2."

Pytest & testing — what to say if asked

Testing is a near-guaranteed interview question. Three rules: be honest about scope (it's a smoke test, not an eval), explain WHY that was the right choice for this product, and have one concrete piece of code in your head you can walk through.

"How did you test the MatchScout pipeline?"
"Pytest smoke test on every push — about 50 lines, two test cases covering the pure stage functions (filter, ranker, no-LLM recommendation builder). It catches structural breakage — broken imports, schema validation, wrong rank set, hallucinated creator IDs — in under a second. The real eval isn't CI; it's the two-arm outcome A/B dashboard. CI is the tripwire, the dashboard is the verdict."
"Why no quality threshold in CI?"
"Synthetic golden sets ossify and stop reflecting real usage. For a recommender on a live marketplace, the truth is downstream gig outcomes — acceptance rate, gig success rate, business rating — segmented by treatment arm and prompt version. CI checks that the code still runs; the dashboard checks that the model still works. Different jobs, different gates. Putting a faithfulness threshold in CI would gate every push on a metric that may not predict the metric I actually care about."
"Why pytest specifically?"
"De-facto standard for Python. Plain function tests, plain assert statements — pytest rewrites assertion bytecode so a failed comparison shows you both sides without helper methods. Fixtures give dependency-injected setup that composes cleanly. For a single-developer PoC the boilerplate-free style matters; for production the fixture system scales to shared DB / model / API setup."
"What does your test NOT catch?"
"It bypasses the LangGraph graph and calls the stage functions directly. That keeps CI side-effect-free (no DB writes) and means no ANTHROPIC_API_KEY secret in CI. The cost: it doesn't catch graph-wiring bugs — bad routing functions, miswired edges, a broken persist node. Those are caught by the local --all run before any push, and by LangSmith tracing in Phase 5. For a low-traffic PoC the tradeoff is fine; at higher traffic I'd add an integration test that invokes the graph against an in-memory or fixture DB."
"How do you handle test isolation / state between tests?"
"Fixtures with the right scope. sample_gig uses scope='module' so db.list_gigs() runs once and the value is reused across tests in the file — cheap setup, no per-test repetition. Because the tests treat the fixture as read-only and never write to the DB, they're trivially re-runnable in any order. Wider scopes are a footgun only when tests mutate shared state — which is why I designed the smoke test around the pure stage functions instead of recommend_creators()."
⚠ What NOT to say
  • Don't claim "comprehensive test coverage." Two tests on the no-LLM path is a smoke test, not coverage. Senior interviewers catch overclaims immediately.
  • Don't say "I evaluate the LLM in CI." You don't — the LLM arm isn't called in CI. Be honest about the scope; interviewers value the design reasoning ("CI is the tripwire, outcomes are the eval") more than a misleading claim.
  • Don't use assert for production input validation. assert statements are stripped under python -O. Use if not X: raise ValueError(...) for runtime checks. Volunteering this distinction when asked about defensive code is a senior signal.

GitHub Actions & CI — what to say if asked

If pytest is the "how do you test it?" question, GitHub Actions is the "how does that get enforced?" follow-up. Rules of engagement: lead with the mental model (config-as-code, ephemeral runners), name the trigger granularity, and have an honest answer about monorepo handling.

"How does your CI work end-to-end?"
"GitHub Actions, defined as a YAML file at .github/workflows/smoke.yml. On every push or PR that touches matchscout-onemyle/, GitHub spins up a fresh Ubuntu runner, clones the repo, installs deps, seeds a SQLite DB from committed CSVs, and runs pytest. About 30 seconds end-to-end. Pass / fail shows up as a commit status check on GitHub. CI is config-as-code — the YAML is reviewable in PRs alongside the code it tests."
"What's an 'action' in GitHub Actions?"
"A reusable package — actually a git repo — that a workflow step calls via uses: owner/repo@version. actions/checkout@v4 is the official one that clones your code; actions/setup-python@v5 is the official one that installs Python. Inside the workflow you mix uses: steps (call someone's package) with run: steps (literal shell). I pin to major version tags like @v4 — you get patches automatically; for security-critical workflows I'd pin to a full SHA."
"How often does CI run?"
"Once per push, not once per commit. A push of five commits fires the workflow once, against the tip commit. The paths: filter checks the union of files changed across all commits in the push, so if any commit touched a matching path the workflow fires. For rapid iteration I'd add a concurrency: block that cancels in-flight runs when a newer push arrives — saves minutes without losing the latest signal."
"How do you handle CI for multiple sub-projects in one repo?"
"GitHub only discovers workflows in .github/workflows/ at the repo root — it doesn't scan subdirectories. For a monorepo with multiple independent sub-projects (MatchScout, P10 platform, etc.), the standard pattern is one workflow file per sub-project at the root, each with a tight paths: filter. A push touching MatchScout only fires MatchScout's workflow. When CI shapes are similar, I'd consolidate via reusable workflows (workflow_call) — define the generic Python-smoke workflow once, call it from thin per-project wrappers. For now I have one workflow because I have one CI'd project."
"What does it cost?"
"Free for public repos. Private repos get 2,000 Linux runner minutes/month on the free tier; macOS minutes cost 10× and Windows 2×. A 30-second smoke test barely registers. For commercial-scale CI you'd add caching (actions/cache) and a concurrency block to avoid wasting minutes on obsolete in-flight runs."
"What about secrets / API keys?"
"Set at the repo level — Settings → Secrets and variables → Actions — and accessed in YAML as ${{ secrets.NAME }}. The MatchScout smoke test deliberately needs none, because the test runs the no-LLM path only. That was a design choice — keeping CI free of API-key dependencies means anyone can fork and run CI without setting up secrets, and there's no risk of a leaked token in a workflow log."
⚠ What NOT to say
  • Don't claim you have multi-environment deploy pipelines. The MatchScout CI is a smoke gate, not a deployment workflow. If asked about deploy: "deployment is out of scope for the PoC — it'd be added in Phase 5+ alongside observability." Honest scope is a senior signal.
  • Don't overclaim security posture. You're pinning to @v4 (a moving major-version tag), not full SHAs. That's a deliberate tradeoff for a small project — call it out as a tradeoff, not as best practice.
  • Don't say "GitHub Actions is configured in the repo settings." It's configured by the YAML file. Repo settings are for secrets and access control — the workflow logic itself lives in .github/workflows/.
  • Don't conflate CI minutes with API cost. A pytest run on a GitHub runner is free up to the quota; it has nothing to do with the LLM API spend on MatchScout's actual recommendations (~$0.03/gig Arm 2).
