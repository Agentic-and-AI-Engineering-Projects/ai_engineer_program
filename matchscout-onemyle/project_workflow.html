Phase 0 — Project Setup Done
~1 hour · Goal: working dev environment

What it is: Stand up the project skeleton. Install dependencies. Configure API keys.

  1. Create folder structure (matchscout/, data/, prompts/, eval/, pm/)
  2. Write requirements.txt with all libraries (LangGraph, Anthropic, Faker, sentence-transformers, Ragas, DeepEval, LangSmith, LangFuse)

  5. Smoke test — verify imports work

Phase 1 — Synthetic Marketplace Data Done
~1 day · Goal: realistic test dataset

What it is: Generate a synthetic Onemyle marketplace — fake creators, fake businesses, fake historical matches. Since real Onemyle data isn't available, this lets us build and test the system.

  1. Define the 8-category schema (Food, Auto, Retail, Beauty, Fashion, Fitness, Travel, Home/Real Estate) with sub-categories, content types, and adjacency map → data/categories.json
  2. Build the generator — Faker-based Python script that creates realistic creator and business profiles
  3. Generate 400 creators with portfolios, locations, budgets, follower counts
  4. Generate 300 businesses with content needs, sizes, locations, budgets
  5. Generate 150 historical matches with outcomes (success/failed/no_response) where outcome severity correlates with structural compatibility
  6. Save all to CSV files in data/
📦 Deliverable: data/creators.csv, data/businesses.csv, data/matches.csv — the marketplace catalog + history

Phase 2 — Build the Cascade Pipeline Active
~3-4 days · Goal: working prediction pipeline end-to-end

What it is: Build the 4-stage cascade architecture that takes a creator + business pair and predicts match success.

Important — what data the pipeline uses:

  • The pipeline reads the EXISTING creators.csv + businesses.csv from Phase 1 (no new data generated)
  • It predicts on NEW pairings — the 119,850 creator-business combinations that AREN'T in matches.csv
  • matches.csv is used for two things: (a) historical context the agent can cite ("this creator has 23 past gigs at 4.7 rating"), (b) the eval set later (Phase 3) to measure agent accuracy
  1. Stage 1 — Filter (rules): drop pairs that fail basic checks (wrong category, wrong location, no budget overlap)
  2. Stage 2 — Vector ranker: use sentence-transformers (small, free, local) to embed profiles and rank candidates by semantic similarity. We use the small model because Stage 3 LLM does the deep reasoning — Stage 2 just narrows candidates.
  3. Stage 3 — LLM agent: LangGraph state machine + Claude reasons about top candidates and outputs structured prediction (probability, reasoning, risk flags, recommended action)
  4. Stage 4 — Quality gate: per-prediction RUNTIME check (different from offline eval in Phase 3) — validates schema, confidence threshold, faithfulness, no hallucinated fields, self-consistency. Failed predictions get retried with a corrective prompt OR rejected.
  5. Pipeline orchestrator: runs Stage 1 → 2 → 3 → 4 end-to-end
  6. Smoke-test on a few creator-business pairs; verify output shape
📦 Deliverable: Run python -m matchscout.pipeline --business biz_001 and get top 5 ranked creator predictions with reasoning

Phase 3 — Eval Framework Pending
~3-4 days · Goal: measurable quality, locked thresholds, CI gating

What it is: Without measurement, the AI is "vibes." Build a multi-layer eval system that quantifies quality and prevents regressions.

  1. Build golden test set: hand-label 50 creator-business pairs with expected outcomes (success/fail) and expected reasoning themes → eval/golden_set.json
  2. Wire up Ragas: measures faithfulness — did the agent's reasoning cite signals actually present in the input?
  3. Wire up DeepEval: pytest-style assertions — output schema valid, no invented fields, self-consistent action
  4. Wire up Promptfoo: A/B test 3 prompt variants on golden set, pick the best
  5. Build regression suite: full eval runner with thresholds (precision ≥ 75%, faithfulness ≥ 0.85, cost ≤ $0.30)
  6. Wire up CI: GitHub Actions runs eval on every push; blocks PR if quality drops
📦 Deliverable: Full eval framework. Numbers like "precision 87%, faithfulness 0.84, $0.18 per prediction" we can put in PRD and resume.

Phase 4 — Observability Wiring Pending
~1-2 days · Goal: traceable, debuggable, cost-monitored predictions

What it is: Without observability, when something goes wrong you can't debug it. Wire up tracing and cost monitoring.

  1. LangSmith integration: every LLM call traced — inputs, outputs, latency, token counts
  2. LangFuse integration: aggregated dashboards — cost per prediction, daily spend, p95 latency
  3. Local audit log: append-only CSV of every prediction with cost + outcome
  4. Per-prediction cost tracking: dollar cost computed and logged for each call
📦 Deliverable: Live dashboards. Click any prediction → see full trace. Watch cost trends in real time.

Two kinds of eval — Stage 4 vs Phase 3

This is the most-confused part of the system. Both Stage 4 (in Phase 2) and Phase 3 do "eval" but at different scales:

Stage 4 (Quality Gate)Phase 3 (Eval Framework)
RunsEvery prediction at request timeEvery code push (CI) + during dev
AgainstTHIS specific predictionThe 50-pair golden set (fixed)
DecidesSurface this prediction OR retry OR rejectIs this version good enough to ship
Failure responseBlock one bad prediction from reaching userBlock a bad code change from being merged
Speed requiredFast (~50ms per check)Can be slow (runs whole golden set)
ToolsPydantic, custom Python checks, lightweight RagasRagas (heavy), DeepEval, Promptfoo, regression suite

Analogy: Stage 4 = airport security (per-passenger). Phase 3 = airline maintenance audit (per-fleet). You need both.

What eval actually measures (broader than prompts)

A common misconception: "eval is for prompt engineering." Wrong. Eval is the measurement layer that informs ALL engineering decisions:

DecisionEval tells you...
Should I tweak the prompt?Did the new variant beat the old one?
Should I switch models? (Sonnet → Opus)Is the quality gain worth 5x cost?
Should I change architecture? (single LLM → cascade)Did adding stages hurt or help?
Should I tighten the gate?Are we rejecting too many good predictions?
Should I add more context to the prompt?Does richer input improve faithfulness?
Should I switch sentence-transformer model?Does Stage 2 miss good candidates?

Without eval, every change is a guess. Promptfoo (one tool in the eval framework) IS specifically about prompt iteration — but the broader eval framework is about quality regardless of what changed.
