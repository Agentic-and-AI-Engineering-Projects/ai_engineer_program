Phase 2 — Recommender pipeline (3 stages × 2 arms) Done
~3-4 days · Goal: working gig-driven recommender end-to-end

What it is: Build the gig-driven recommender. python recommend_creators.py --gig-id GIG_ID runs the full pipeline: Stage 1 (rules filter) → Stage 2 (vector ranker) → arm-routed Stage 3 → writes 3 CreatorRecommendation rows to SQLite.

Important — how data flows:

  • Input: one open gig from the gigs table
  • Treatment arm assigned at runtime: 10% random → Arm 1 (no-LLM), 90% → Arm 2 (LLM). Recorded on the gig row.
  • Past gigs read from the gigs table (status='completed' / 'failed' rows) when Arm 2 — for the business AND for each top-10 candidate
  • Profile descriptions read as stored fields on Creator + Business — used by Stage 2 embedding (both arms)
  • Output: 3 rows in recommendations table per gig (rank 1, 2, 3). For Arm 2, also includes reasoning + strengths + risks + key_signals.
  1. Stage 1 — filter.py: rules filter. Inputs: gig + creators pool. Three rules: location compatible, budget overlap, content_type overlap. Returns N candidates.
  2. Stage 2 — ranker.py: cosine similarity. Embedding text per side = niche_tags + profile_description + primary_category + secondary_categories + primary_subcategories. sentence-transformers/all-MiniLM-L6-v2 (local). Returns ranked list X.
  3. Stage 3 — agent.py: LangGraph state machine with two routes based on gig.treatment_arm:
    • no_llm: emit top 3 of X by cosine score. No LLM call. reasoning, strengths, risks fields are null.
    • llm: take top 10 of X; for each, query the gigs table for up to 10 most recent completed gigs (WHERE assigned_creator_id = X AND status='completed' ORDER BY completed_at DESC LIMIT 10); compute per-creator metrics (success count, fail count, follower count, avg rating) and per-metric ranks within the 10; load the versioned prompt template (prompts/arm2_v1.txt); call Claude with the formatted prompt; parse + validate output via Pydantic; emit top 3 with reasoning + strengths + risks + key_signals.
  4. Prompt template — prompts/arm2_v1.txt: the LLM ranking instructions (versioned, edited as a file, not inlined in code). Stamped on each recommendation via prompt_version column.
  5. Pipeline — pipeline.py: orchestrates Stage 1 → Stage 2 → arm assignment → Stage 3 → write recommendations to SQLite.
  6. Entry point — recommend_creators.py: CLI script taking --gig-id, stand-in for the future "Recommend Creators" UI button.
  7. Smoke-test: run pipeline on 5 gigs, verify recommendations are written, manually inspect quality via VS Code SQLite Viewer.
📦 Deliverable: Run python recommend_creators.py --gig-id gig_001 and get 3 ranked recommendations written to SQLite. Run on all 30 open gigs in ~2 minutes. Inspect via VS Code SQLite Viewer.

Phase 3 — CI smoke test only Done
~0.5 day · Goal: catch broken code, not bad LLM output

What it is: Deliberately minimal. The real eval is outcome-based (Phase 4). The only thing CI checks is that the pipeline runs end-to-end on a few dummy gigs and produces schema-valid output. No synthetic golden set, no quality thresholds, no faithfulness gates.

Why so light? Pre-deploy eval on synthetic data is intellectually satisfying but doesn't predict production outcomes — and it adds engineering overhead (hand-label, maintain). Mature production teams deploy LLM features behind A/B tests with minimal pre-deploy eval. This project follows that pattern.

  1. Write matchscout/tests/test_pipeline_smoke.py: ~30 lines of pytest. Run pipeline on 2-3 dummy gigs (one for each arm). Assert: output is valid Pydantic, 3 recommendations per gig, no exceptions raised.
  2. Add .github/workflows/smoke.yml: runs pytest -q matchscout/tests/ on every push.
  3. Do NOT build: golden_set.json, run_golden_set.py, check_thresholds.py, regression_suite.py — these are not part of this design.
📦 Deliverable: CI runs in < 60 seconds and catches "code is broken" before merge. Bad LLM output is detected by the Phase 4 outcome dashboard, not by pre-deploy eval.

Phase 4 — Outcome dashboard + prompt iteration loop Done
~1-2 days · Goal: causal measurement of LLM lift + closed-loop prompt iteration

What it is: The entire eval surface for this project. Reads completed gigs from SQLite, segments by treatment_arm and prompt_version, computes outcome metrics, runs chi-squared significance, renders a Streamlit dashboard. When metrics regress, the simplified remediation toolkit (Appendix) drives prompt iteration.

  1. dashboard_batch.py — reads gigs + recommendations where status='completed'.
  2. Group by (treatment_arm, prompt_version) — two arms (no_llm, llm), with the LLM arm sub-grouped by prompt version (arm2_v1, arm2_v2, ...).
  3. Compute per group: N, acceptance rate, top-1 selection rate, gig success rate when accepted, composite good-outcome rate.
  4. Chi-squared significance — Arm 1 vs Arm 2 (scipy.stats.chi2_contingency).
  5. Render to Streamlit (dashboard.py) — side-by-side table, bar charts per metric, drill-down to specific gigs with LangSmith trace links.
  6. Prompt iteration loop: when a metric regresses or plateaus, follow the appendix remediation chain — LangFuse spots drift → LangSmith reads bad traces → Ragas/DeepEval diagnose → edit prompt template → bump PROMPT_VERSION → deploy as arm2_v2 → dashboard segments confirm recovery. Log each version's rationale in prompts/README.md.
  7. Alerting (optional) — flag if Arm 2 falls below Arm 1 on composite metric (suggests prompt regression).
📦 Deliverable: streamlit run matchscout/dashboard.py shows a two-arm comparison with chi-squared p-values, segmented by prompt version. Demonstrable to Onemyle stakeholders.

One eval scope (outcome-based)

Quality eval is a single layer: the Phase 4 outcome dashboard segmenting by treatment_arm and prompt_version. There is no pre-deploy golden set, no CI quality gate, no faithfulness threshold blocking PRs. CI runs only a schema smoke test that catches broken code, not bad LLM output.

What's deliberately missing: pre-deploy synthetic golden set, hand-labeled quality thresholds, regression suite blocking PRs. Mature production teams use A/B tests instead, and so does this project.

What survives from the eval toolkit: Ragas, DeepEval, Promptfoo, LangSmith, LangFuse are used as DEV-TIME ITERATION TOOLS during prompt refinement (see appendix). They are NOT in CI.

What eval actually measures (broader than prompts)

A common misconception: "eval is for prompt engineering." Wrong. Eval is the measurement layer that informs ALL engineering decisions:

DecisionEval tells you...
Should I tweak the prompt?Did the new variant beat the old one?
Should I switch models? (Sonnet → Opus)Is the quality gain worth 5x cost?
Should I change architecture? (single LLM → cascade)Did adding stages hurt or help?
Should I tighten the gate?Are we rejecting too many good predictions?
Should I add more context to the prompt?Does richer input improve faithfulness?
Should I switch sentence-transformer model?Does Stage 2 miss good candidates?

Without eval, every change is a guess. Promptfoo (one tool in the eval framework) IS specifically about prompt iteration — but the broader eval framework is about quality regardless of what changed.

Appendix — Simplified Remediation Playbook

When the Phase 4 outcome dashboard shows Arm 2 is not beating Arm 1 (or a new prompt version is worse than the previous one), follow this playbook. One library, one job. No nested conditionals.

SymptomToolWhat you do
Arm 2 not beating Arm 1 (LLM-with-history ≤ no-LLM) Ragas Run faithfulness on Arm 2 reasoning. If score is low, the LLM is hallucinating past gigs (citing pairs that don't exist in the gigs table). Tighten prompt to require literal references to gigs-table rows.
Outputs broken, inconsistent, or off-schema DeepEval Run the assertion suite: rank ∈ {1,2,3}, no fabricated creator IDs, historical_signals reference real gigs-table rows, length within bounds. Fix what fails.
Want to test a new prompt variant before deploying it Promptfoo Run the new prompt against a sample of recent real gigs alongside the current prompt. Compare outputs side-by-side. If better, deploy as a new prompt version and measure in the outcome dashboard.
One specific recommendation looks wrong LangSmith Open that gig's trace. See exact inputs, LLM reasoning, output tokens. Decide if it's a prompt / data / model issue.
Trends over time, drift, cost-creep LangFuse Dashboard shows rolling acceptance / success / cost per arm. If a metric drifts, drill into LangSmith traces for that time window.

How they chain together (the loop)

LangFuse dashboard shows Arm 2 drifting down
        ↓
Open LangSmith — read 5 recent Arm 2 traces
        ↓
Suspect hallucination → Ragas faithfulness sweep on a sample
        ↓
Confirmed: LLM citing fake past gigs
        ↓
Edit prompts/arm2_v1.txt → save as prompts/arm2_v2.txt
        ↓
Promptfoo preview: run new prompt on recent gigs alongside v1
        ↓
Deploy v2 (bump PROMPT_VERSION) → outcome dashboard segments confirm recovery
        ↓
DeepEval re-checks structural integrity of v2 outputs

Five tools, one job each. None of these run in CI — they are dev-time tools used during prompt iteration. CI runs only the schema smoke test. The eval that decides whether the LLM earns its cost is the outcome dashboard, not these tools.

Appendix — pandas DataFrame Primer

Quick reference for the DataFrame patterns used in data_loader.py. Read this if you ever need a refresher on what df[col], .apply(), or eval() are doing.

What is a DataFrame?

A DataFrame (df) is a 2-D table — rows × columns — living in Python memory. Think spreadsheet or SQL result set. Each row is one record (e.g. one creator); each column is one attribute across all records.

            id            name  primary_category  follower_count   niche_tags
   0   cre_0001    John Smith              Food            8421   "['vegan']"
   1   cre_0002    Mary Jones            Beauty           24010   "['organic', 'cruelty-free']"
   2   cre_0003    Sam Lee               Fitness            512   "[]"
   ...
   399 cre_0400    Lisa Park              Auto             1893   "['classic-cars']"

What is df[col]?

df[col] selects one column and returns it as a 1-D Series — a labeled list with row indices preserved.

df["niche_tags"]
# 0      "['vegan']"
# 1      "['organic', 'cruelty-free']"
# 2      "[]"
# ...
# 399    "['classic-cars']"
# Name: niche_tags, dtype: object

The number on the left is the row index; the value on the right is the cell content; dtype: object tells you the column type.

What does df[col] = df[col].apply(fn) do?

Column-wise transformation. Three steps in one line:

df[col]                  # SELECT  — grab one column as a Series
df[col].apply(fn)        # MAP     — run fn on EACH cell, return a new Series
df[col] = ...            # ASSIGN  — overwrite the original column with the result

Conceptually, .apply() is pandas' equivalent of a for loop over the column:

# What apply is doing under the hood:
new_values = []
for value in df[col]:
    new_values.append(fn(value))
df[col] = new_values

The .apply() form is faster (vectorized internally) and more idiomatic.

Why it's needed in data_loader.py

When pandas saved creators.csv, list-typed fields like niche_tags = ["pizza", "burgers"] got serialized as strings:

"['pizza', 'burgers']"   ← stored in CSV as a string, not a list

Reading the CSV back gives every list column full of strings that look like lists but aren't. _parse_list_column calls eval() on each cell to convert the string back to a real Python list. After the apply loop, those columns hold actual list objects — which Pydantic accepts in Creator(**row.to_dict()).

What does eval(value) do?

eval() takes a string of Python code and executes it as if you'd typed it into the interpreter, returning the result.

value = "['pizza', 'burgers']"   # a string
result = eval(value)              # runs it as Python
# result is now: ['pizza', 'burgers']   ← a real list
Safety note: eval() will execute anything valid Python — including __import__('os').system('rm -rf /'). Safe here because we wrote the CSV ourselves. In production code, prefer ast.literal_eval(value), which only parses literals (numbers, strings, lists, dicts, tuples, booleans, None) and refuses function calls or imports. Better still: store list columns as JSON and use json.loads.

The three branches of _parse_list_column

def _parse_list_column(value):
    if pd.isna(value) or value == "":      # Case 1: missing / empty
        return []
    if isinstance(value, list):            # Case 2: already a list (defensive)
        return value
    return eval(value)                     # Case 3: string that looks like a list
CaseWhen it firesWhy
1 — missing/emptyCell is NaN or empty stringReturn [] so Pydantic still gets a valid list; doesn't crash
2 — already a listDefensive — won't fire on CSV inputFuture-proof: protects against being called on a DataFrame built from JSON or constructed in memory
3 — string-of-a-listThe expected case after read_csvConvert "['pizza']" → ['pizza'] via eval

Mental model: the function is a per-cell type adapter. Input could be missing / list / string-of-a-list; output is always a list. That uniformity is what lets Pydantic-based loading downstream work without further branches.

Why order matters: pd.isna(value) must run first. If the cell is NaN, value == "" returns False (NaN compares unequal to everything), isinstance(NaN, list) is False, so it would fall through to eval(NaN) — which crashes. The NaN check short-circuits before that happens.

pandas dtypes — and why object is special

Every column has a declared dtype:

dtypeWhat it storesNotes
int64Integers onlyStrict, fast, NumPy-backed
float64Floats and NaNStrict, fast
boolTrue/FalseStrict, fast
datetime64[ns]TimestampsStrict, fast
objectAnything Python — strings, lists, dicts, mixed typesThe escape hatch — slow but flexible

The numeric dtypes are strict and tightly stored. object dtype is the wildcard — each cell is just a Python pointer to any object, so one column can legally hold strings, lists, dicts, mixed types — pandas won't complain.

That's why the apply loop in data_loader.py works without "changing" the column type. The column is object before the loop (cells are strings) and object after (cells are lists). Dtype unchanged; per-cell type changed.

df["niche_tags"].dtype                    # object
type(df["niche_tags"].iloc[0])            # str (before apply)

df["niche_tags"] = df["niche_tags"].apply(_parse_list_column)

df["niche_tags"].dtype                    # object  (still!)
type(df["niche_tags"].iloc[0])            # list    (after apply)

Mental model:

  • Strict dtypes (int64, float64, bool, datetime64) → like a typed array. Fast, memory-efficient, restrictive.
  • object dtype → like a Python list of references. Slow, flexible, holds anything.

Numeric/scientific code lives in strict dtypes. Real-world tabular data with messy fields (lists, dicts, mixed types) lives in object. niche_tags, budget_range_per_gig, and friends are all object columns.
