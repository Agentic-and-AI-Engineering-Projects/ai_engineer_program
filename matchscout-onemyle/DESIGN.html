1. Overview

What MatchScout Does

MatchScout is an AI-powered creator recommender for Onemyle's two-sided marketplace. When a business posts a gig, MatchScout surfaces the top 3 creators most likely to deliver a successful collaboration — with reasoning grounded in either their past gig history or their profile descriptions. A holdout control arm (no-LLM baseline) lets us causally measure the LLM's lift on business outcomes.

One-line description

"For Onemyle's marketplace operations team, MatchScout is an AI assistant that recommends the top 3 creators for every newly posted gig — reasoning over each candidate's past performance or profile to maximize acceptance rate and gig success rate, measured against a no-LLM control arm."

2. Problem Statement

The Problem MatchScout Solves

Marketplace dynamics

Onemyle is a two-sided marketplace. Both sides depend on match quality:

  • Creators waste effort pitching businesses that aren't a real fit → frustration, churn
  • Businesses get poor content from mismatched creators → frustration, churn
  • Marketplace loses transactions, GMV, reputation

Today, matching is largely manual or browse-based. Both sides spend time evaluating fit. Bad matches happen — and they cause double-sided churn.

What we're building toward

An AI layer that scores match quality automatically — informing recommendations, surfacing risky introductions for proactive support, and improving the overall marketplace experience.

3. Scope (V1 PoC)

V1 PoC Scope

In Scope

  • Synthetic marketplace data: creators + businesses (CSV catalog) + past gigs + open gigs + recommendations (SQLite)
  • Profile descriptions (Instagram-bio style free text) stored on each creator and business as a permanent field — synthesized via Claude one-time for PoC (stands in for what users write at signup)
  • Gig-driven pipeline triggered by python recommend_creators.py --gig-id GIG_ID (PoC stand-in for the "Recommend Creators" button in a future UI)
  • Stage 1 hard filter (3 rules): location · budget · content type overlap
  • Stage 2 vector cosine ranker over (niche_tags + profile_description + primary_category + secondary_categories + primary_subcategories) → ranked list X
  • Two-arm A/B assignment per gig: Arm 1 no-LLM control (10% random, top 3 by cosine), Arm 2 LLM (90%, top 10 → LLM picks 3 with reasoning)
  • LangGraph state machine for Arm 2 with a single versioned prompt template (prompts/arm2_v1.txt); prompt_version stamped on each recommendation
  • Outcome eval — acceptance rate, top-1 selection rate, gig success rate, per arm and per prompt version, with chi-squared significance
  • Streamlit dashboard — two-arm comparison, with drill-down to LangSmith traces
  • Simplified dev-time remediation toolkit — Ragas / DeepEval / Promptfoo / LangSmith / LangFuse, one job each (NOT a CI gate)
  • CI = schema smoke test only (pytest, ~2 dummy gigs through pipeline, asserts Pydantic output validates)
  • Per-recommendation cost tracking ($0 for Arm 1; ~$0.30 for Arm 2)
  • Reasoning is logged to SQLite for post-hoc analysis but NOT surfaced to the business — the business sees only the 3 creator picks
  • Full PM artifact set (PRD, ICP, eval plan, GTM brief, risk register)

Out of Scope (V2+ territory)

  • Web UI (the "Recommend Creators" button + creator display) — V2; replaced by CLI entry point in V1
  • Pre-deploy synthetic golden set + threshold-based CI quality gates — explicitly avoided (synthetic eval doesn't predict production outcomes)
  • FastAPI service wrapper (V2 / maps to P10)
  • Pinecone / managed vector DB (V2 / P10)
  • Multi-cloud LLM routing (V2 / P10)
  • Reliability patterns: circuit breaker, fallback (V2 / P10)
  • Suggested-offer generation and outreach DM drafting — V2 add-on, separate workflow
  • Position-bias counter (randomizing display order of top 3) — V2 enhancement
  • Real Onemyle data integration (V2)
  • Production deployment, real users (V3)
4. Architecture

Gig-Driven Recommender — 3 Stages × 3 Eval Arms

A gig posted by a business is the trigger. The pipeline narrows from the full creator catalog to 3 recommended creators, with a treatment-arm split that lets us causally measure the LLM's lift over a no-LLM control.

Why the system orients around the Gig
Real marketplaces work in gig terms: a business posts a job, the platform recommends a shortlist, the business picks one, the gig succeeds or fails. The Gig is the unit of work the user actually cares about — so the system orients around it. Recommendations become first-class entities tied to a gig, and outcomes flow back into eval automatically.

5. Components — Detailed

Component Breakdown

filter.py — Stage 1 (Hard Filters)

def stage1_filter(creator, gig) -> bool:
    """Pure function — returns True if creator is structurally compatible with the gig."""

    # Location compatibility
    if creator.location != gig.location_required:
        if not (creator.remote_friendly and gig.remote_acceptable):
            return False

    # Budget overlap
    if creator.budget_range_per_gig[1] < gig.budget_range[0]: return False
    if creator.budget_range_per_gig[0] > gig.budget_range[1]: return False

    # Content type overlap (at least one shared)
    if not set(creator.content_types) & set(gig.content_needs):
        return False

    return True

Three rules — location, budget, content type. No category gating (handled in Stage 2 via embedding). No LLM. Runs in microseconds per pair.

ranker.py — Stage 2 (Vector Similarity)

Why we use the small sentence-transformer model
Stage 2 uses all-MiniLM-L6-v2 (22M params, 384-dim, ~80MB, free, local) — not the larger all-mpnet-base-v2. For Stage 2's job (narrowing N candidates to 10), the small model is fast enough and good enough. Stage 3's LLM does the deep reasoning over historical metrics afterwards. 
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")  # local, free, fast

def embedding_text(entity):
    """Textual representation for embedding — same shape for creator + business."""
    return " ".join([
        " ".join(entity.niche_tags),
        entity.profile_description,
        entity.primary_category,
        " ".join(entity.secondary_categories),
        " ".join(entity.primary_subcategories),
    ])

def stage2_rank(gig, candidates, top_k=10):
    """Rank Stage 1 candidates by cosine similarity to the gig-posting business."""
    business = load_business(gig.business_id)
    business_vec = model.encode(embedding_text(business))
    candidate_vecs = model.encode([embedding_text(c) for c in candidates])

    similarities = cosine_similarity([business_vec], candidate_vecs)[0]
    ranked = sorted(zip(candidates, similarities), key=lambda x: -x[1])
    return ranked[:top_k]

Embeddings can be pre-computed and cached. Same embedding function on both sides of the marketplace — symmetric representation.

agent.py — Stage 3 (LangGraph LLM Agent)

Prompt is a versioned template file, not inline code
The prompt template lives in prompts/arm2_v1.txt. agent.py loads it by version, formats in runtime data, and calls the LLM. Each recommendation row records its prompt_version, so the outcome dashboard can segment metrics by prompt version — this is how prompt iteration is empirically driven, not vibe-driven.

pipeline.py — Orchestrator

import random
from matchscout import db, filter, ranker, agent

CONTROL_FRACTION = 0.10   # 10% of gigs go to no-LLM control

def recommend_creators(gig_id: str):
    """Entry point — invoked by `python recommend_creators.py --gig-id gig_001`.
    Runs the full pipeline and writes 3 CreatorRecommendation rows to SQLite."""
    gig = db.get_gig(gig_id)
    all_creators = load_all_creators()

    # Stage 1 — hard filter
    candidates = [c for c in all_creators if filter.stage1_filter(c, gig)]

    # Stage 2 — vector rank
    ranked = ranker.stage2_rank(gig, candidates, top_k=10)

    # Treatment arm assignment
    arm = "no_llm" if random.random() < CONTROL_FRACTION else "llm"
    db.update_gig(gig_id, treatment_arm=arm)

    if arm == "no_llm":
        # Arm 1: top 3 by cosine, no LLM
        top_3 = [c for c, _sim in ranked[:3]]
        recommendations = [
            db.CreatorRecommendation(
                gig_id=gig_id, creator_id=c.id, rank=i+1,
                source_arm="no_llm", prompt_version=None,
                reasoning=None,
            )
            for i, c in enumerate(top_3)
        ]
    else:
        # Arm 2: top 10 → LLM picks top 3 using versioned prompt
        top_10 = [c for c, _sim in ranked[:10]]
        recommendations = agent.invoke(gig, top_10)

    db.write_recommendations(recommendations)
    return recommendations

Arm 1 rows have source_arm="no_llm", prompt_version=null, and most narrative fields (reasoning, strengths, risks) are null. Schema is uniform so dashboard aggregation can scan both arms in one query.

Important: the reasoning, strengths, risks fields are stored for post-hoc analysis and prompt iteration — they are NOT surfaced to the business in the UI. The business sees only the 3 creator names and basic profile info.

One unified gigs table — no separate past_gigs
Historical and active gigs live in the same SQLite table, distinguished by the status field. "Past gigs for creator X" is SELECT * FROM gigs WHERE assigned_creator_id = X AND status = 'completed' ORDER BY completed_at DESC LIMIT 10. This avoids duplicating schema and keeps a single source of truth for the gig lifecycle. The seed data in matches.csv is loaded into this same table with status='completed' (or 'failed' / 'no_response' based on outcome).

V1 (PoC) vs V2 (Production)

V1 — Manual / On-Demand

For the PoC, MatchScout is invoked manually:

V2 — Production Triggers (documented, not built)

For productionization, three high-value trigger moments:

  1. On match initiation — when creator applies or business invites. Premium scoring before introduction. Highest leverage moment.
  2. On gig post — when business posts a new gig. Surface top 5 creator recommendations. Proactive.
  3. On profile view — when user views a candidate's profile. On-demand match score badge. Discovery experience.

Plus background jobs for cache freshness and regression detection.

12. Eval Framework

Multi-Layer Eval

Eval is outcome-based, not pre-deploy threshold-based
Every gig produces 3 recommendations and (eventually) an outcome. Outcomes are the eval. There is no synthetic golden set, no CI quality gate, no pre-deploy threshold check. The single dashboard segmenting by treatment_arm and prompt_version is the entire eval surface — and it's all that matters, because the only quality question that matters is "did the LLM beat the no-LLM baseline on real user behavior."

The two arms

Arm Assignment How recommendations are produced Cost per gig
Arm 1 — No-LLM control 10% of gigs, random Top 3 by cosine similarity from Stage 2. No reasoning. No LLM call. $0
Arm 2 — LLM 90% of gigs Stage 2's top 10 + each candidate's last-10-gigs history + per-metric ranks → LLM applies versioned prompt template → top 3 with reasoning. ~$0.30

If the LLM is adding value: Arm 2 > Arm 1 on composite good-outcome rate. If not, apply the remediation playbook below — and if remediation fails to close the gap, the LLM isn't earning its cost and we should shrink Arm 2.

Prompt iteration loop

The prompt is the primary tuning surface. Iteration is empirically driven:

1. Deploy prompts/arm2_v1.txt → measure on real gigs over N days
2. Dashboard shows a weakness (e.g. acceptance rate plateaued at 68%)
3. Read 5-10 LangSmith traces of low-rank-#1 selections → form hypothesis
4. Edit prompt → save as prompts/arm2_v2.txt → bump PROMPT_VERSION
5. Deploy v2 → measure → compare segmented metrics in dashboard
6. v2 wins? Lock in. v2 loses? Roll back to v1. Log the experiment in prompts/README.md

Promptfoo, Ragas, and DeepEval are dev-time tools used during this loop — not as CI gates. They run on demand against a sample of recent recommendations.

Simplified remediation playbook (dev-time iteration tools)

One library, one job. No CI gating.

SymptomToolAction
Arm 2 not beating Arm 1 on composite outcome rateRagasRun faithfulness on a sample of recent Arm 2 outputs. If LLM is citing past gigs that don't exist in the gigs table, tighten the grounding instruction in the prompt template.
Outputs broken, inconsistent, off-schemaDeepEvalRun assertion suite — rank ∈ {1,2,3}, no fabricated creator IDs, all cited gigs exist in the gigs table with status=completed. Fix prompt or schema.
Want to test a new prompt variant before deployingPromptfooRun new prompt against a sample of recent gigs alongside current prompt. Compare outputs side-by-side. Deploy as new version if better, measure in dashboard.
One specific recommendation looks wrongLangSmithOpen the trace for that gig. See exact inputs, LLM reasoning, output. Diagnose.
Trends over time, drift, cost-creepLangFuseRolling per-arm and per-prompt-version metrics. If a metric drifts, drill into LangSmith for that window.

Chain in practice: LangFuse spots Arm 2 drifting → LangSmith reads 5 bad traces → Ragas confirms hallucinated history → edit prompt template → Promptfoo previews the fix → deploy as arm2_v2 → dashboard segments confirm recovery.

CI — schema smoke test only

One small pytest check runs on every push: pipeline runs on 2-3 dummy gigs and asserts the output validates against the Pydantic schema. This catches "code is broken" — not "LLM output is bad." That's the only CI eval check, intentionally.

Appendix A — The End-to-End Story

A Narrative Walk-Through of MatchScout

This appendix tells the same system as the rest of the document — but as a story. Easier to understand if you're new to the architecture, useful as an interview narrative, and a sanity check that the design coheres.

The setup

Imagine Maya, a Boston food photographer. And Tavola, a Boston fine-dining restaurant looking for photography. Both signed up to Onemyle. Neither knows the other exists.

Onemyle has hundreds of creators and hundreds of businesses across 8 categories. When a business posts a gig, the platform wants AI to surface the 3 best creators for that specific gig.

So they build MatchScout — a 3-stage pipeline with a 2-arm A/B that finds quality matches efficiently and proves the LLM is worth the cost.

Before MatchScout can run, two pieces of preparation happen:

  1. Profile descriptions — every creator and business writes a short bio (Instagram style) at signup. Stored as a permanent field on their profile.
  2. Embeddings — each creator and business gets its profile fields (niche_tags + bio + categories + subcategories) concatenated into a single string and converted to a vector using a small, free, local sentence-transformer. Stored alongside the profile. Refreshed when the profile changes.

A user moment — Tavola posts a gig

Tavola posts: "Food photography for our new tasting menu. Boston, $500–$1000, 2 reels + photo set within 2 weeks."

This creates a new gig row in SQLite. Tavola clicks "Recommend Creators." That fires recommend_creators.py --gig-id gig_001, which runs the pipeline.

Stage 1 — Hard filter (~10ms, free)

Takes all creators and drops the ones that are structurally incompatible: wrong location (and not remote-friendly), no budget overlap, no content-type overlap. After this filter we have, say, 80 candidates.

Stage 2 — Vector ranker (~50ms, free)

Tavola's embedding is compared against each of the 80 candidates' embeddings via cosine similarity. Returns a ranked list X. This catches subtle vibe fit — a creator with bio mentioning "fine dining and natural lighting" ranks higher than one focused on "fast food and event coverage" even though both pass Stage 1.

Treatment arm assignment

Random coin flip: 10% chance → Arm 1 (no_llm), 90% → Arm 2 (llm). The result is stamped on the gig row for later eval.

Stage 3 — Arm-routed (Arm 1: free, instant; Arm 2: ~$0.30, ~3s)

If Arm 1: take the top 3 of X by cosine score. Write 3 CreatorRecommendation rows. Done. No LLM call. Reasoning fields are null.

If Arm 2: take the top 10 of X. For each one, query the gigs table for their last-10 most recent completed gigs (WHERE assigned_creator_id = X AND status = 'completed' ORDER BY completed_at DESC LIMIT 10). Compute per-creator metrics (success count, fail count, follower count, avg rating) and per-metric ranks within the 10. Load the current prompt template (prompts/arm2_v1.txt), format in the gig brief + metrics table + recent gig history. Send to Claude. Claude returns ranked top 3 with reasoning, strengths, risks, key_signals per creator.

The 3 CreatorRecommendation rows are written to SQLite with prompt_version="arm2_v1" stamped on each.

The result Tavola sees

Just the 3 creator profiles. No reasoning, no scores, no risk flags. The reasoning is in SQLite — useful for post-hoc analysis and prompt iteration, but irrelevant to Tavola's decision. Tavola picks Maya. That sets gig.assigned_creator_id. Two weeks later the gig completes successfully → gig.outcome = "success". This row is now an eval data point.

Behind the scenes (continuously)

During Arm 2's LLM call:

  1. LangSmith captured the full trace — the formatted prompt sent to Claude, the response, token counts, latency. The platform team can debug "why did Maya rank #1?" by clicking through the trace.
  2. LangFuse logged the cost (~$0.30 for this gig) into rolling per-arm and per-prompt-version dashboards.

What happens when the platform team improves the prompt

A few weeks in, the team notices Arm 2's top-1 selection rate is plateauing at 56%. They want to push it higher.

They open LangSmith and read 10 traces where Tavola-style businesses picked rank #2 or #3 instead of rank #1. They notice the LLM is over-weighting follower count for high-budget gigs. They open prompts/arm2_v1.txt, edit one principle ("for budgets above $1,500, weigh reliability over reach"), save as prompts/arm2_v2.txt, and bump PROMPT_VERSION.

They deploy. Every recommendation from this point forward stamps prompt_version="arm2_v2". The outcome dashboard now segments metrics by version.

Three weeks later: v2 acceptance rate is 71%, v1 was 64%. Chi-squared p-value: 0.03. v2 wins. They lock it in. The experiment log gets a new entry in prompts/README.md.

No PR was blocked. No golden set was consulted. The dashboard told them what to do.

The full lifecycle in one mental picture

BUSINESS posts a gig + clicks "Recommend Creators" │ ▼ PIPELINE runs: Stage 1 hard filter → Stage 2 vector rank → arm assignment → Stage 3 (no_llm or llm) │ ▼ 3 CreatorRecommendations written to SQLite │ │── LLM trace logged to LangSmith │── Cost/latency to LangFuse │ ▼ BUSINESS picks a creator → gig.assigned_creator_id set │ ▼ GIG completes → outcome set (success / failed / no_response) │ ▼ NIGHTLY DASHBOARD BATCH aggregates outcomes per (treatment_arm, prompt_version) MEANWHILE (offline / on demand): │ TEAM observes outcome dashboard → spots an issue │ ▼ Reads LangSmith traces → diagnoses with Ragas / DeepEval │ ▼ Edits prompts/arm2_v1.txt → saves as arm2_v2.txt → bumps PROMPT_VERSION │ ▼ Promptfoo previews new prompt on recent gigs │ ▼ DEPLOY v2 → outcome dashboard segments confirm (or refute) the improvement

Why each piece matters

  • Stage 1 — without it, you'd embed and score every creator. Too slow at scale.
  • Stage 2 — without it, you'd hand the LLM the full candidate pool. Wastes Stage 3 budget and dilutes input quality.
  • Stage 3 LLM (Arm 2) — without it, you'd just have cosine ranking. No reasoning over historical signals, no per-creator strengths/risks analysis.
  • Arm 1 control — without it, you can't tell whether Stage 3 is earning its cost. Causal eval requires a baseline.
  • Versioned prompt templates — without them, prompt iteration becomes git-diff-driven instead of outcome-driven.
  • Outcome dashboard — without it, you ship prompt changes blindly. Quality silently drifts.
  • Observability (LangSmith / LangFuse) — without it, when something goes wrong, you can't diagnose.

Each layer earns its place.

What success looks like at the end of the PoC

A working system where:

  • Tavola posts a gig → MatchScout writes 3 ranked creators to SQLite in ~3 seconds for ~$0.30 (Arm 2) or instantly for free (Arm 1)
  • Every recommendation is traced in LangSmith and stamped with its prompt version
  • The Streamlit dashboard shows a measurable causal lift of Arm 2 over Arm 1 — with chi-squared significance
  • Prompt iteration is empirical: every new prompt version's outcomes are tracked separately, so the team knows whether a change actually helped
  • CI runs only a schema smoke test — broken code is caught fast, but no synthetic golden set is burning engineering time
  • The PM artifacts (PRD, ICP, eval plan, GTM brief, risk register) document the strategic thinking

Plus a public GitHub repo and a credible Onemyle-initiative entry on the resume.
