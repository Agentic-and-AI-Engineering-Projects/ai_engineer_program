Kubernetes Primer for AI Engineers

Just enough Kubernetes to deploy and operate agentic AI systems in production. The conceptual map, the primitives you'll actually use, the commands you'll type every day, and the 90-second interview answer. Anchored to the k3s home-server setup used across this curriculum.

Sections: 1. Why Kubernetes 2. The cluster anatomy 3. Pods — the atomic unit 4. Workload controllers 5. Networking & Services 6. Config & Secrets 7. Storage 8. The kubectl model 9. Commands cheatsheet 10. k3s & flavors 11. Interview answer

1. Why Kubernetes

Kubernetes (often abbreviated k8s — k + 8 letters + s) is a container orchestration platform. You hand it Docker containers and a desired-state spec ("run 3 copies of this, restart if any die, route traffic to them"); it makes that state real and keeps it real.

The problems it solves

  • Container scheduling. You have 50 machines and 200 containers. Where does each one run? Which machine has room? Kubernetes decides.
  • Self-healing. A container crashes → restart it. A machine dies → reschedule its containers elsewhere. No human intervention.
  • Rolling deployments. Replace v1 with v2 one container at a time, checking health between steps. Roll back automatically on failure.
  • Service discovery + load balancing. "How do I reach the database?" → ask Kubernetes by name, traffic gets routed to a healthy container.
  • Declarative config. You describe what you want in YAML; Kubernetes makes it happen. Same YAML produces same outcome every time, in any environment.

Why an AI Engineer cares

Production agentic AI systems land on Kubernetes for the same reasons every other distributed system does — but with an extra dimension: GPU scheduling. When you need to deploy an inference workload pinned to specific GPU nodes, route traffic to it, scale it up under load, and roll out a model upgrade without downtime, Kubernetes is the dominant answer.

The cleanest one-liner: Kubernetes turns "I have 50 machines and 200 containers" into "I have a desired-state spec; the platform makes it real and keeps it real."

2. The cluster anatomy

A cluster is one or more machines coordinated as a single compute pool. Every Kubernetes cluster has two roles:

RoleWhat it doesTypical count
Control plane (formerly "master")The brain. Receives your YAML, decides what runs where, monitors cluster state.1 (dev) or 3+ (HA prod)
Worker nodesWhere your containers actually run.1 to thousands

Control plane components

ComponentJob
kube-apiserverThe single entry point. Every kubectl command, every internal Kubernetes process, every cluster mutation flows through it. Stateless front door.
etcdThe cluster's database. Stores all state — what's running, what's desired, what's healthy. The only stateful component on the control plane.
kube-scheduler"Pod X needs to run somewhere. Which node?" Considers resource requests, affinity, taints, etc.
kube-controller-managerRuns reconciliation loops. "Desired: 3 replicas. Actual: 2. Spawn one more." Repeat forever for every controller (Deployment, ReplicaSet, Node, Service, etc.)
cloud-controller-managerInterfaces with cloud APIs (AWS, GCP, Azure) for things like provisioning load balancers, volumes, or nodes.

Worker node components

ComponentJob
kubeletThe node's agent. Talks to apiserver, receives "run this pod" instructions, manages container lifecycle.
kube-proxyImplements Service networking — routes traffic to pods, manages iptables/IPVS rules.
Container runtimeThe actual container engine — containerd (modern default), or older Docker. Pulls images, starts/stops containers.

3. Pods — the atomic unit

A Pod is the smallest deployable unit in Kubernetes. Not a container — a wrapper around one or more containers that share network namespace, storage volumes, and lifecycle.

Important properties

  • One IP per pod. All containers in a pod share the same IP and port space. They can talk to each other on localhost.
  • Shared volumes. Containers in a pod can share filesystem space via mounted volumes.
  • Co-scheduled, co-located. A pod's containers always run on the same node.
  • Ephemeral. Pods come and go. Treat them as cattle, not pets. Don't store state in a pod's local filesystem.
  • You rarely create pods directly. You create a higher-level controller (Deployment, StatefulSet, etc.) that creates pods for you.

Minimal pod YAML

apiVersion: v1
kind: Pod
metadata:
  name: matchscout-api
  labels:
    app: matchscout
spec:
  containers:
  - name: api
    image: myregistry/matchscout:v1.2.3
    ports:
    - containerPort: 8000
    env:
    - name: ANTHROPIC_API_KEY
      valueFrom:
        secretKeyRef:
          name: api-keys
          key: anthropic

Why pods exist instead of just containers

The pod abstraction lets you group tightly-coupled containers that must share a network. The canonical example is the sidecar pattern — your app container plus a logging-shipper container that tails a shared volume. Both must be on the same machine; both must die together; both must talk on localhost. The pod expresses that.

4. Workload controllers

You almost never create Pods directly. You create higher-level controllers that own pods and reconcile them. Six common ones:

4.1 Deployment

What it is: Stateless web apps, APIs, agents. The default choice for almost everything.

What it manages: A ReplicaSet, which manages Pods. You set replicas: 3 and Deployment ensures 3 healthy pods exist.

What it does well: Rolling updates, rollbacks, scaling.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: matchscout-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: matchscout
  template:
    metadata:
      labels:
        app: matchscout
    spec:
      containers:
      - name: api
        image: myregistry/matchscout:v1.2.3
        ports:
        - containerPort: 8000

4.2 ReplicaSet

Maintains a stable set of replica Pods. You never create ReplicaSets directly — Deployments create them for you. Worth knowing about because rolling updates work by creating a new ReplicaSet and gradually shifting pods from old to new.

4.3 StatefulSet

What it is: For workloads where pod identity matters — databases, Kafka brokers, Elasticsearch nodes.

What's different from Deployment: Each pod gets a stable name (db-0, db-1, db-2) and stable storage. Pods come back as the same identity after restart. They start in order (0, then 1, then 2) and stop in reverse.

4.4 DaemonSet

What it is: Runs exactly one pod on every node. Used for node-level agents — log shippers, metrics agents, network plugins.

4.5 Job

What it is: Runs a pod to completion. Used for batch work — database migrations, one-shot model evaluations, ingest runs.

4.6 CronJob

What it is: A Job that runs on a schedule (cron syntax). Used for scheduled tasks — nightly report generation, recurring data ingest, periodic model retraining.

5. Networking & Services

Pods come and go; their IPs change. You can't hardcode "talk to pod 10.244.3.17" — that pod could die in 30 seconds. The solution: Service.

What a Service is

A Service is a stable network endpoint in front of a set of pods, selected by labels. Service has a long-lived IP and DNS name; pods behind it can come and go.

apiVersion: v1
kind: Service
metadata:
  name: matchscout-svc
spec:
  selector:
    app: matchscout              # any pod with this label is behind the Service
  ports:
  - port: 80                      # Service port
    targetPort: 8000              # Pod port
  type: ClusterIP                 # ← type matters; see below

Service types

TypeReachable fromWhen to use
ClusterIP (default)Inside cluster onlyInternal app-to-app traffic — most common
NodePortOutside cluster via <node-ip>:<port> where port is in 30000–32767Quick external exposure for dev/k3s setups
LoadBalancerOutside cluster via a cloud load balancerProduction cloud (AWS/GCP/Azure) — provisions an ELB / GLB automatically
ExternalNameDNS alias to an external servicePointing inside-cluster names at outside-cluster databases

NodePort — the home-server pattern

Used heavily in this curriculum's k3s setup (192.168.1.156). Kubernetes opens a port (e.g. 30002) on EVERY node in the cluster; traffic to <any-node-ip>:30002 gets routed to a healthy pod behind the Service. The Kanban server, Kafka broker, and MongoDB are all exposed this way:

type: NodePort
ports:
- port: 80
  targetPort: 8000
  nodePort: 30002              # the port on the node's external IP

This is "good enough" for home labs and dev clusters. Production cloud deployments use LoadBalancer or Ingress instead.

Ingress — the proper external entry point

An Ingress is a layer-7 (HTTP/HTTPS) router that sits in front of Services. One Ingress controller, one cloud LB, many Services routed by path or hostname:

spec:
  rules:
  - host: api.matchscout.com
    http:
      paths:
      - path: /v1/recommend
        backend:
          service:
            name: matchscout-svc
            port: { number: 80 }
      - path: /v1/health
        backend:
          service:
            name: healthcheck-svc
            port: { number: 80 }

Ingress controllers (NGINX, Traefik, AWS ALB Ingress Controller) implement the actual routing. k3s ships with Traefik out of the box.

6. Config & Secrets

Hardcoding configuration into container images is an anti-pattern. Kubernetes provides two primitives:

ConfigMap — non-secret config

apiVersion: v1
kind: ConfigMap
metadata:
  name: matchscout-config
data:
  PROMPT_VERSION: "arm2_v3"
  CONTROL_FRACTION: "0.5"
  LANGSMITH_PROJECT: "matchscout-prod"

Mount as env vars or files into the pod.

Secret — sensitive config

Same shape as ConfigMap but base64-encoded and meant for credentials. RBAC-protected, encrypted at rest in etcd.

apiVersion: v1
kind: Secret
metadata:
  name: api-keys
type: Opaque
data:
  anthropic: c2stYW50LXh4eHh4...        # base64-encoded
  openai: c2stcHJvai14eHh4eHh...

In production: use external secret managers (AWS Secrets Manager, HashiCorp Vault) with the External Secrets Operator. Kubernetes Secrets are not actually encrypted unless you configure encryption-at-rest for etcd.

7. Storage

Pods are ephemeral; their local disk dies with them. Persistent state needs Volumes.

ObjectRole
VolumeStorage attached to a Pod's lifecycle. Survives container restarts but not pod deletion (for most volume types).
PersistentVolume (PV)Cluster-level storage resource. Provisioned by admin or dynamically by a StorageClass.
PersistentVolumeClaim (PVC)A pod's request for storage. "I need 10 GB, fast SSD." Kubernetes matches PVCs to PVs.
StorageClassRecipe for dynamic provisioning. "When someone asks for storage, create an EBS volume of this type." Cloud-specific.

For stateful workloads (databases on StatefulSet), each pod gets its own PVC, dynamically provisioned by the StorageClass. The pod can die and respawn elsewhere; the data follows it.

8. The kubectl model

kubectl is the CLI. It talks only to the apiserver. Everything you do is a structured API call.

Two interaction styles

Imperative — quick, ad-hoc

kubectl run mybox --image=busybox -- sleep 3600
kubectl scale deployment matchscout-api --replicas=5
kubectl delete pod matchscout-api-7b8d9-x4q2v

Declarative — production discipline

# Write YAML, version it in git
kubectl apply -f deployment.yaml

# Update YAML, re-apply — Kubernetes reconciles the difference
kubectl apply -f deployment.yaml

# Delete by reference to the same YAML
kubectl delete -f deployment.yaml

Production always uses declarative. The YAML in git is the single source of truth; the cluster state is reconciled toward it. This is the foundation of GitOps (ArgoCD, Flux).

Context & namespace — what most newcomers miss

Context = "which cluster am I pointing at?" You can have many in ~/.kube/config (home k3s, AWS EKS prod, GCP GKE dev).

Namespace = "which logical partition inside that cluster?" Namespaces isolate workloads — matchscout-prod, matchscout-staging, shared-monitoring.

kubectl config get-contexts                  # list configured clusters
kubectl config use-context prod              # switch to prod cluster
kubectl get pods -n matchscout-prod          # list pods in a namespace
kubectl config set-context --current --namespace=matchscout-prod   # default to that namespace

9. kubectl commands cheatsheet

Inspect

kubectl get pods                                       # list pods (current namespace)
kubectl get pods -A                                    # all namespaces
kubectl get pods -o wide                               # include node and IP
kubectl get all                                        # everything in current namespace
kubectl get nodes                                      # cluster nodes
kubectl get deployments                                # deployments
kubectl get services                                   # services
kubectl get pvc                                        # persistent volume claims

kubectl describe pod matchscout-api-7b8d9-x4q2v        # detailed pod info, recent events
kubectl describe node node1                            # detailed node info, resource usage

Logs & exec

kubectl logs matchscout-api-7b8d9-x4q2v                # logs from pod
kubectl logs -f matchscout-api-7b8d9-x4q2v             # follow (tail -f equivalent)
kubectl logs matchscout-api-7b8d9-x4q2v --previous     # logs from the previous container restart
kubectl logs -l app=matchscout                         # logs from all pods matching label

kubectl exec -it matchscout-api-7b8d9-x4q2v -- bash    # shell into the pod
kubectl exec matchscout-api-7b8d9-x4q2v -- ls /app     # run one command

Modify

kubectl apply -f deployment.yaml                       # create or update from YAML
kubectl delete -f deployment.yaml                      # delete by YAML
kubectl delete pod matchscout-api-7b8d9-x4q2v          # delete a pod (will be respawned if managed)

kubectl scale deployment matchscout-api --replicas=5   # change replica count
kubectl rollout status deployment matchscout-api       # watch a rolling update
kubectl rollout undo deployment matchscout-api         # roll back to previous version
kubectl rollout history deployment matchscout-api      # see deploy history

kubectl edit deployment matchscout-api                 # open YAML in $EDITOR, save → apply

Networking & debugging

kubectl port-forward svc/matchscout-svc 8080:80        # forward a service to localhost
kubectl port-forward pod/matchscout-api-7b8d9 8000     # forward a pod port

kubectl get events --sort-by='.lastTimestamp'          # cluster events, recent first
kubectl top pods                                        # CPU/memory usage by pod
kubectl top nodes                                       # CPU/memory usage by node

Cleanup

kubectl delete deployment matchscout-api               # delete a deployment (and its pods)
kubectl delete namespace matchscout-staging            # nuke a whole namespace

10. k3s & flavors of Kubernetes

Several Kubernetes distributions exist for different use cases:

DistributionUse case
k3sSingle binary, <50 MB, ideal for edge, IoT, home labs, dev. Used in this curriculum's home server (192.168.1.156) for the Kanban app + Kafka broker + Mavic Drone MongoDB.
minikube / kindSingle-node local dev clusters on your laptop.
kubeadmBare-metal production with manual setup. The reference implementation.
EKS (AWS)Managed control plane, you own worker nodes. The enterprise standard on AWS.
GKE (Google)Managed K8s on GCP. Often considered the most polished managed offering.
AKS (Azure)Managed K8s on Azure.
OpenShift (Red Hat)Enterprise distribution with built-in CI/CD, RBAC, etc. Common in regulated industries.

k3s specifics (the home-lab pattern)

  • Single binary install: curl -sfL https://get.k3s.io | sh -
  • SQLite-backed by default (no etcd) — perfect for single-node use; switch to embedded etcd for HA
  • Traefik bundled as the default Ingress controller
  • ServiceLB bundled for LoadBalancer support without cloud APIs
  • kubectl works the same as on any other cluster — copy /etc/rancher/k3s/k3s.yaml to your laptop's ~/.kube/config and point at the server IP

The trade-off: k3s is wonderful for learning, edge, IoT, and personal projects. For enterprise prod with compliance/audit/HA requirements, you typically reach for EKS/GKE/AKS or OpenShift.

11. The 90-second interview answer

"Kubernetes is a declarative container orchestration platform. You hand it a YAML spec — 'run 3 copies of this image, expose port 8000, restart anything that dies' — and it makes that real and keeps it real through reconciliation loops. The cluster has two layers: a control plane (apiserver as the entry point, etcd as the state store, scheduler placing pods on nodes, controller-manager running the reconciliation loops) and worker nodes (kubelet talking to apiserver, kube-proxy implementing service networking, containerd running containers).

The atomic unit is the Pod — one or more containers sharing network namespace and storage, co-scheduled on the same node. You almost never create pods directly. You use higher-level controllers: Deployment for stateless apps with rolling updates, StatefulSet for databases where pod identity matters, DaemonSet for node-level agents, Job and CronJob for batch and scheduled work.

For networking, Services give you a stable IP and DNS name in front of an ever-changing set of pods, selected by labels. Four types: ClusterIP for internal traffic (default), NodePort for cheap external exposure on every node's IP, LoadBalancer that provisions a cloud LB in EKS/GKE/AKS, and ExternalName as a DNS alias. For HTTP/HTTPS routing, an Ingress controller sits in front of Services and routes by path or hostname.

Config and secrets are first-class objects: ConfigMaps for non-sensitive config, Secrets for credentials (in production, external secret managers feed into them). Persistent storage is PersistentVolumeClaim against StorageClass-provisioned PersistentVolumes — that's how StatefulSets keep state across pod restarts.

For AI workloads, the patterns are: Deployment for inference APIs (with HorizontalPodAutoscaler for traffic-based scaling), Deployment with nvidia.com/gpu resource requests for GPU pinning, StatefulSet for vector DBs and Kafka, CronJob for nightly evals, External Secrets Operator pointed at AWS Secrets Manager for credentials. For local dev and edge use I run k3s — single binary, SQLite-backed, Traefik bundled — and the same kubectl commands work against EKS or GKE for production."
