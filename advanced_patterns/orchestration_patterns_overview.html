Agentic Orchestration Patterns — Overview

Five common patterns for orchestrating multi-step or multi-agent work in production AI systems. Each is presented as: use case → architecture diagram → code skeleton → when to use vs not use → where the LLM decides what.

The spectrum, from least to most LLM-driven orchestration:

PatternWhat the LLM decidesWhat the code decides
1. Sequential PipelineNothing about flowEverything (fixed order)
2. Conditional RouterWhich of N pre-defined branches to takeThe set of options
3. Orchestrator-WorkerWHAT subtasks exist (and how many)WHO runs them (single worker type), parallel dispatch
4. Supervisor / HierarchicalWHAT, WHO, and WHEN (full delegation)The agent pool
5. ReAct LoopEvery step iterativelyThe loop + tool definitions
The unifying lens — "Who decides the flow?" Every pattern can be classified by who answers two questions at runtime:
  1. Which step runs next? — flow decisions
  2. What does that step do? — work decisions
Sequential Pipeline answers both with code. ReAct answers both with the LLM. The middle three patterns split the responsibility differently. Pick the pattern by deciding how much of the flow you want code to lock down vs how much you want the LLM to drive at runtime.

How frameworks map onto these patterns

The patterns are framework-agnostic. The same five patterns show up across LangGraph, CrewAI, OpenAI Agents SDK, AutoGen, Claude Agent SDK, and vanilla Python. Quick map:

PatternLangGraph wayCrewAI way
Sequential Pipelineadd_edge chainProcess.sequential with tasks in list order
Conditional Routeradd_conditional_edges(no first-party equivalent; rare in CrewAI)
Orchestrator-WorkerOrchestrator node + Send API + Worker node + Synthesizer nodePossible via manual task chaining; CrewAI's first-party version is more supervisor-flavored
SupervisorBuild it yourself with conditional edges + LLM routerProcess.hierarchical with a manager_agent
ReAct LoopCyclic graph with add_conditional_edges looping backSingle-agent Crew with tools and verbose=True

The framework choice doesn't change which pattern you're implementing. The pattern is the shape; the framework is how you express it.

1. Sequential Pipeline

Use case: A daily newsletter generator. Every morning at 7am, it (1) fetches the top 10 news articles, (2) summarizes each with an LLM, (3) ranks by relevance, (4) formats into HTML, (5) sends via email. Same 5 steps, same order, every day.

Architecture

flowchart LR A[Fetch articles] --> B[Summarize each] B --> C[Rank by relevance] C --> D[Format HTML] D --> E[Send email]

Code skeleton (LangGraph)

def fetch_articles(state):
    articles = newsapi.fetch_top(10)
    return {"articles": articles}

def summarize(state):
    summaries = [llm.summarize(a) for a in state["articles"]]
    return {"summaries": summaries}

def rank(state):
    ranked = sorted(state["summaries"], key=relevance_score, reverse=True)
    return {"ranked": ranked}

def format_html(state):
    html = render_template("newsletter.html", items=state["ranked"])
    return {"html": html}

def send_email(state):
    smtp.send(state["html"])
    return {}

graph = StateGraph(NewsState)
graph.add_node("fetch", fetch_articles)
graph.add_node("summarize", summarize)
graph.add_node("rank", rank)
graph.add_node("format", format_html)
graph.add_node("send", send_email)

graph.set_entry_point("fetch")
graph.add_edge("fetch", "summarize")
graph.add_edge("summarize", "rank")
graph.add_edge("rank", "format")
graph.add_edge("format", "send")
graph.add_edge("send", END)

Where the LLM decides what

Nothing about flow. The LLM is used inside a node (the summarize step calls an LLM) but it doesn't influence WHICH step runs next or HOW MANY times. The code defines the entire flow at design time.

Same pattern, CrewAI flavor

CrewAI's Process.sequential is just this pattern in CrewAI's vocabulary. Tasks declared in a list with explicit agent=... per task; execution follows list order. Same as the LangGraph add_edge chain above — the framework changes, the pattern doesn't.

from crewai import Agent, Task, Crew, Process

fetcher = Agent(role="News Fetcher", ...)
summarizer = Agent(role="Summarizer", ...)
formatter = Agent(role="Formatter", ...)
sender = Agent(role="Sender", ...)

tasks = [
    Task(description="Fetch articles", agent=fetcher),
    Task(description="Summarize each", agent=summarizer, context=[tasks[0]]),
    Task(description="Format HTML", agent=formatter, context=[tasks[1]]),
    Task(description="Send email", agent=sender, context=[tasks[2]]),
]

crew = Crew(
    agents=[fetcher, summarizer, formatter, sender],
    tasks=tasks,
    process=Process.sequential,    # ← Sequential Pipeline pattern
)
crew.kickoff()

P5 ReviewCrew uses exactly this shape: three tasks (fetch_task, review_task, summary_task) with hardcoded agent assignments, executed in list order. No LLM decides what runs next.

Use when: The steps are known business requirements. The order never changes. Each step depends predictably on the previous. You want maximum determinism and easy debugging.
Don't use when: The steps depend on input content (different inputs need different work). The order should adapt. You're tempted to add lots of if/else inside nodes to switch behavior — that's a signal you need a router or orchestrator instead.

2. Conditional Router

Use case: Customer support triage. A user message arrives. An LLM classifies it as one of three categories: billing, technical, or sales. Each category goes to a different specialist handler. The set of categories is FIXED — code knows about exactly three.

Architecture

flowchart TD A[User message arrives] --> B[Classifier LLM] B -.-> C[billing_handler] B -.-> D[technical_handler] B -.-> E[sales_handler] C --> F[Send response] D --> F E --> F F --> G([END])

Code skeleton (LangGraph)

def classify(state):
    """The LLM here makes ONE decision: which branch?
    The set of possible answers is fixed at design time."""
    response = llm.invoke(f"""Classify this message as one of:
    'billing', 'technical', 'sales'.
    Message: {state['message']}
    Return only the category name.""")
    return {"category": response.strip()}

def route(state) -> str:
    """Router function: pure (state) -> str. Picks the next node."""
    return state["category"]   # returns "billing", "technical", or "sales"

def billing_handler(state):
    return {"reply": llm.invoke(f"Handle this billing question: {state['message']}")}

def technical_handler(state):
    return {"reply": llm.invoke(f"Handle this tech question: {state['message']}")}

def sales_handler(state):
    return {"reply": llm.invoke(f"Handle this sales question: {state['message']}")}

graph.add_node("classify", classify)
graph.add_node("billing", billing_handler)
graph.add_node("technical", technical_handler)
graph.add_node("sales", sales_handler)
graph.set_entry_point("classify")

graph.add_conditional_edges("classify", route, {
    "billing":   "billing",
    "technical": "technical",
    "sales":     "sales",
})
graph.add_edge("billing", END)
graph.add_edge("technical", END)
graph.add_edge("sales", END)

Where the LLM decides what

One decision: which of the 3 pre-defined branches. The code already knows all possible destinations. The LLM picks one. After that single decision, the flow is fixed.

Use when: The work splits into a SMALL, FIXED set of well-defined branches. You want the LLM to make a single routing decision. Examples: intent classification, language detection, severity triage.
Don't use when: The branches aren't well-defined or the count varies (use orchestrator-worker). The decision is mechanical and rule-based (use plain if/else in a node, no LLM needed).

3. Orchestrator-Worker

Use case: A research assistant. The user submits a topic. An LLM decomposes it into N research questions (the number and content vary per topic). N parallel workers each research one question via web search. A synthesizer LLM folds findings into a coherent report.

Architecture

flowchart TD A[User topic] --> B[Orchestrator LLM
decomposes into N questions] B -.Send API.-> C1[Worker 1
question 1] B -.Send API.-> C2[Worker 2
question 2] B -.Send API.-> C3[Worker N
question N] C1 --> D[Synthesizer LLM] C2 --> D C3 --> D D --> E([END])

Code skeleton (LangGraph with Send API)

def orchestrator(state):
    """LLM decomposes topic into N questions. N varies by topic."""
    response = llm.invoke(f"""Decompose '{state['topic']}' into 3-5
    specific research questions. Return JSON array.""")
    questions = json.loads(response)
    return {"questions": questions}     # could be 3, 4, or 5 items

def dispatch(state) -> list[Send]:
    """Spawn one parallel worker per question. N is decided at runtime."""
    return [Send("worker", {"question": q}) for q in state["questions"]]

def worker(state):
    """Single worker type. Each instance gets a different question."""
    findings = web_search(state["question"], max_results=3)
    return {"findings": findings}   # operator.add reducer accumulates

def synthesizer(state):
    """LLM folds all worker findings into coherent narrative."""
    text = "\n".join(str(f) for f in state["findings"])
    response = llm.invoke(f"Synthesize: {text}")
    return {"summary": response}

graph.set_entry_point("orchestrator")
graph.add_conditional_edges("orchestrator", dispatch, ["worker"])
graph.add_edge("worker", "synthesizer")
graph.add_edge("synthesizer", END)

Where the LLM decides what

WHAT subtasks exist and how many. The orchestrator LLM might generate 3 questions for one topic and 7 for another. The code dispatches one worker per question. WHO handles each is fixed (always the single worker function). WHEN they run is fixed (always in parallel). The LLM controls the SHAPE of the work, the code controls the dispatch mechanism.

Three runs, identical code, different execution shapes

TopicLLM-generated questionsWorker count
"quantum computing"["What are qubits?", "What hardware exists?", "What problems can it solve?"]3
"ancient Roman history"["When did Rome fall?", "Who were the emperors?", "How was the Senate?", "Roman law?", "The army?"]5
"Paris weather today"["Current temp?", "Today's forecast?"]2

Same code, same graph. Different worker counts emerged from what the LLM produced.

Use when: The set of subtasks depends on the input. You don't know at design time how many or what they are. Each subtask is independent (parallelizable). You have one or a small fixed set of worker types.
Don't use when: The subtasks are always the same (sequential pipeline). Different subtasks need different worker types AND the LLM should pick which (supervisor). The subtasks aren't independent and need to share intermediate state.

4. Supervisor / Hierarchical (CrewAI Process.hierarchical)

Use case: A content production team. Manager agent reviews a request and decides at each step: "I need the researcher first" → researcher returns sources → "now I need the writer to draft" → writer returns draft → "the editor needs to polish before publishing" → editor refines. Three SPECIALIZED agents with different skills; the manager LLM picks WHO does WHAT and WHEN, dynamically.

Architecture

flowchart TD A[User request] --> B[Manager Agent LLM] B -.decides who & when.-> C[Researcher Agent] B -.decides who & when.-> D[Writer Agent] B -.decides who & when.-> E[Editor Agent] C --> B D --> B E --> B B --> F[Final output] F --> G([END])

Note: every arrow back to the manager — the manager keeps control after each specialist returns, deciding the next move.

Code skeleton (CrewAI)

from crewai import Agent, Task, Crew, Process

manager = Agent(
    role="Content Manager",
    goal="Coordinate research, writing, and editing to produce a polished article",
    backstory="Senior editor at a magazine. Picks the right specialist for each phase.",
)

researcher = Agent(
    role="Researcher",
    goal="Find authoritative sources on the assigned topic",
    backstory="Detail-oriented investigator with web search skills.",
    tools=[web_search_tool],
)

writer = Agent(
    role="Writer",
    goal="Draft engaging long-form content from research",
    backstory="Award-winning journalist with a clear, punchy style.",
)

editor = Agent(
    role="Editor",
    goal="Polish drafts for clarity, accuracy, and tone",
    backstory="Veteran copy editor with a sharp eye for inconsistency.",
)

crew = Crew(
    agents=[researcher, writer, editor],     # available specialists
    tasks=[
        Task(description="Produce an article on {topic}", expected_output="Polished article"),
    ],
    manager_agent=manager,                   # the LLM that decides
    process=Process.hierarchical,            # ← supervisor pattern
)

result = crew.kickoff(inputs={"topic": "AI in healthcare"})

Where the LLM decides what

WHAT, WHO, and WHEN — full delegation. The manager LLM sees the task and the pool of available agents, then dynamically picks who handles what, in what order, and whether to loop back for revisions. Code only defines the agents (their roles/skills); the manager orchestrates everything else.

Same agents, two processes — what changes

The clearest way to internalize the difference between Sequential Pipeline and Supervisor is to write the same crew twice — once with each process. SAME agents, SAME goal, SAME tools. Different process flag changes the entire execution shape:

Process.sequential (Sequential Pipeline)Process.hierarchical (Supervisor)
Task definitionEach task has explicit agent=...Tasks have agent=None — manager assigns
Task orderList order = execution orderManager picks order at runtime
Skip / loopEvery task always runs; no skippingManager can skip tasks, loop back, request revisions
Manager agentNot neededRequired (manager_agent=manager)
CostOne LLM call per task (predictable)One LLM call per task + manager decisions between (variable)
Best whenOrder is known business requirementOrder depends on intermediate output quality

Concrete code-level difference:

# Process.sequential — code decides flow
review_task = Task(
    description="Review the PR diff",
    agent=code_reviewer,                      # ← hardcoded
    context=[fetch_task],                      # ← hardcoded dependency
)
crew = Crew(
    tasks=[fetch_task, review_task, summary_task],
    process=Process.sequential,
)

# Process.hierarchical — LLM decides flow
review_task = Task(
    description="Review the PR diff",
    agent=None,                                # ← manager decides
    # no context — manager decides what flows where
)
crew = Crew(
    agents=[code_reviewer, security_reviewer, tech_writer],
    tasks=[review_task],
    manager_agent=manager,                    # ← supervisor LLM
    process=Process.hierarchical,
)

The mental model: Process flag → orchestration pattern. Process.sequential IS Sequential Pipeline. Process.hierarchical IS Supervisor. CrewAI's process types are direct implementations of the patterns from this overview.

Use when: You have a SET of distinct specialist agents with different skills (researcher, writer, editor — not three generic workers). The flow between them is unpredictable and depends on intermediate output quality. Examples: content production, code-modification across files, multi-step troubleshooting.
Don't use when: The specialists are interchangeable (use orchestrator-worker). The flow is predictable enough to wire as a sequential pipeline. Cost matters more than flexibility (every delegation is a manager LLM call — expensive at scale).

5. ReAct Loop (Reason + Act)

Use case: A tool-using agent for an internal "ask anything" Q&A bot. User asks: "How many failed deployments did we have last week, and what was the root cause of the biggest one?" The agent needs to: query the deployment DB, find failures, look up incident reports, read logs, summarize. Each step depends on the result of the previous step — the agent decides each tool call iteratively.

Architecture

flowchart TD A[User question] --> B[LLM: think + decide tool] B -.decides STOP.-> F[Return answer] B -.decides CONTINUE.-> C[Execute tool] C --> D[Observe result] D --> B F --> E([END])

Code skeleton (LangGraph)

def reason(state):
    """LLM looks at message history + observations, decides:
    - What tool to call next (with args), or
    - That it has enough info to answer (FINAL_ANSWER)"""
    response = llm.invoke(state["messages"], tools=TOOLS)
    return {"messages": [response]}

def execute_tool(state):
    """Run whatever tool the LLM picked, append result to messages."""
    last = state["messages"][-1]
    if last.tool_calls:
        results = [run_tool(tc) for tc in last.tool_calls]
        return {"messages": results}
    return {}

def should_continue(state) -> str:
    """Loop until LLM stops calling tools (signals: I have an answer)."""
    last = state["messages"][-1]
    return "execute" if last.tool_calls else "done"

graph.set_entry_point("reason")
graph.add_conditional_edges("reason", should_continue, {
    "execute": "execute_tool",
    "done":    END,
})
graph.add_edge("execute_tool", "reason")     # ← the CYCLE

Where the LLM decides what

Every step, iteratively. Each turn the LLM looks at the cumulative message history and decides: "Do I call tool X? Tool Y? Or am I done?" The number of iterations is entirely emergent — could be 2, could be 20.

A typical trace

Iteration 1:  LLM → "Call query_db('SELECT * FROM deployments WHERE status=failed AND week=last')"
              Tool returns: [list of 4 failed deployments]
Iteration 2:  LLM → "Call get_incident_report(deploy_id=42)"  (picked the biggest)
              Tool returns: [incident report text]
Iteration 3:  LLM → "Call read_logs(deploy_id=42, timeframe='around failure')"
              Tool returns: [log excerpt]
Iteration 4:  LLM → "I have enough info. Final answer: 4 failures last week. The biggest, deploy-42, failed due to a database migration timeout. Root cause: an unindexed JOIN added in commit abc123."
              No more tool calls → loop exits.
Use when: Open-ended problems where the path isn't known in advance. The agent has tools and the LLM needs to chain them dynamically. Examples: code assistants (Claude Code is a ReAct loop), question-answering over multiple data sources, exploratory data analysis.
Don't use when: The flow is predictable (any other pattern is more efficient). Cost matters and you don't want unbounded LLM calls — ReAct can loop many times. You need fine-grained checkpoint boundaries (every iteration is a checkpoint, which can be expensive). Always pair with recursion_limit and explicit iteration counters.

The senior framing in one paragraph: the five patterns form a spectrum from code-orchestrated (Sequential) to fully LLM-orchestrated (ReAct), with each step trading cost predictability for adaptability. Pick the LEAST LLM-orchestrated pattern that still solves your problem — every extra LLM decision is more tokens, more latency, and more places for the model to pick wrong. Sequential pipelines for known flows. Routers for fixed-branch decisions. Orchestrator-worker when the WHAT varies but the WHO is fixed. Supervisor when WHO matters and the agent pool is specialized. ReAct only when the flow is genuinely open-ended and tool composition is unpredictable.
