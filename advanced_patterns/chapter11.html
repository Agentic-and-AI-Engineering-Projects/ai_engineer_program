Chapter 11 — Multi-Agent Systems

When one agent is no longer enough — and how to know whether you've actually reached that point.

Picture a single Claude Sonnet call with a 2,000-token system prompt that says: "You are a legal research assistant. Extract facts from the document, identify relevant precedents, write a memo. Output JSON." It works for a small document. It hallucinates citations on a medium one. On a long one it loses track of which fact came from which paragraph and the memo conflates two unrelated cases. The output is fluent and confidently wrong.

The natural reaction is to make the prompt longer — add cautions, examples, citation rules. The prompt grows to 4,000 tokens. The hallucinations get more sophisticated but no rarer. Eventually someone on the team writes "we need to split this into stages" and the conversation about multi-agent systems begins.

This chapter is about what that split actually looks like, why it works, what it costs, and — just as important — when it doesn't help.

1. What "multi-agent" actually means

A multi-agent system is one where the work of answering a single user request is split across two or more LLM calls that have different roles. The split can be along several dimensions:

  • By specialization — one agent extracts, another reasons, another writes. Each has a focused system prompt.
  • By perspective — multiple agents argue the same question from different angles, then a synthesizer integrates the results.
  • By scale — N parallel copies of the same agent process N independent tasks.
  • By trust level — a fact-checker agent validates a generator agent's output before it reaches the user.

What this is not:

  • A single agent that calls many tools is not multi-agent. The agent is one LLM with one persona; tools are passive functions. ReAct loops with 20 tool calls still count as one agent.
  • Sequential prompt chains in a notebook are not really multi-agent in the production sense — they're a multi-stage pipeline. Whether you call it "multi-agent" is mostly framing, but the distinction matters when interviewers probe.
  • Calling the same model with different temperatures is not multi-agent. It's sampling.

The cleanest test: can the LLM calls in your system be described as different "people" with different jobs? If yes, it's multi-agent. If they're all the same persona doing different turns of a conversation, it's not.

2. Why you'd ever build one — and when you shouldn't

Multi-agent systems are popular in conference talks and rare in well-run production deployments. There's a reason for the gap.

The case for multi-agent

Three failure modes of single-agent systems push teams toward multi-agent:

(1) System-prompt sprawl. When one agent has to be researcher + reasoner + writer + critic, each role pulls its system prompt in a different direction. The "be cautious" tone the critic needs undermines the "be confident" tone the writer needs. Splitting roles into separate agents lets each prompt stay focused, and quality climbs noticeably.

(2) Failure isolation. If a single-agent pipeline produces a malformed citation in the writing stage, you have nothing — the agent's earlier extraction work and reasoning live only in the conversation history, mixed with the broken final output. If those stages are separate agents with structured handoffs, you can re-run only the failing stage with the previous stage's output intact. The blast radius of a failure shrinks from "whole task" to "one stage."

(3) Specialization beats generalization at quality ceilings. A focused 400-token system prompt for "extract facts as JSON with relevance scoring" outperforms a generalist 2,000-token prompt that has extraction as one of its responsibilities. This isn't because the model is dumber — it's because the focused prompt has more room for examples, edge-case handling, and output schema, all of which raise quality.

The case against

Three things multi-agent systems cost you:

(1) Latency. A 3-stage pipeline is roughly 3× the latency of a single call. If your user expects a 2-second response, a 6-second response feels broken, even if the answer is better. Many production systems are latency-sensitive in ways the engineers building them don't intuitively feel.

(2) Cost. Tokens are spent on every stage's system prompt, every handoff serialization, every revalidation. Cost typically grows 2–5× when going from single-agent to a 3-stage multi-agent system, and that's before retries.

(3) Debugging surface. A single agent has one conversation history to inspect. A multi-agent system has N conversations, M handoffs, intermediate schemas, retry logic, and the question "which stage actually went wrong?" becomes a diagnostic project. Production teams that don't invest in tracing infrastructure spend disproportionate time chasing intermediate-stage bugs that look like final-output bugs.

The honest senior heuristic: default to single-agent. Escalate to multi-agent only when you can name the specific failure mode that escalation solves — not "the output isn't quite right" but "the system prompt is trying to be researcher AND writer and the tones conflict" or "when the writing stage fails I lose the extraction stage's output and have to rerun everything." If you can't name the failure mode, the multi-agent rewrite probably won't help.

3. The four questions every multi-agent design answers

Before picking a topology, every multi-agent system implicitly or explicitly answers four design questions. Asking them out loud is the easiest way to think clearly about what you're building.

Q1. Who decides what happens next?

Possible answers and what they imply:

AnswerImplicationPattern name
Plain Python codeDeterministic, predictable, easy to testPipeline, Swarm
A coordinator LLMFlexible, can handle unanticipated pathsSupervisor-Worker, Dynamic Handoff
The worker agents themselvesMaximum flexibility, hardest to reason aboutDebate, Swarm-with-handoff

This is the most fundamental choice, and it tracks closely with how much the workflow varies between requests. If every request follows the same shape, code routing wins. If requests vary unpredictably, LLM routing wins despite its cost.

Q2. How do the agents share information?

Two clean approaches and one messy one:

  • Structured handoffs. Stage 1 returns a typed object (Pydantic model, JSON schema), stage 2 takes it as input. No shared mutable state. Each handoff is auditable and re-runnable.
  • Shared scratchpad. All agents read and append to a common message log. Easy to start, hard to scale — agents start polluting each other's context with irrelevant detail.
  • (The messy one) Global Python state. Workers mutate a shared dict. Now you have data races on top of LLM nondeterminism. Avoid.

In production, the right answer is almost always typed handoffs. The shared scratchpad is fine for short-lived chains; global state is almost always a mistake.

Q3. What happens when a stage fails?

"Fails" here means several distinct things:

  • The LLM returned malformed JSON that didn't validate against the schema.
  • The LLM call itself errored (rate limit, transient API failure, timeout).
  • The LLM returned valid JSON but the content is wrong (hallucinated citation, missed an extraction).
  • The agent went into an infinite tool-use loop.

Each needs a different response. Schema failures often justify retry-with-feedback ("your output didn't include a 'source' field for fact #3, please reformat"). Transient errors retry with exponential backoff. Content errors typically need a verifier agent (and acceptance that some will get through). Loops need an iteration cap.

A multi-agent system that doesn't explicitly model failure handling per stage is a multi-agent system that surfaces every failure as a user-visible disaster.

Q4. What does the user see, and when?

Single-agent systems are easy here: stream the response. Multi-agent systems have intermediate stages the user often shouldn't see (extraction JSON is not interesting; it's a scaffold for the final memo). The decisions:

  • Show only the final output? Simpler UX, but a 10-second wait feels broken.
  • Show intermediate stages as "thinking" steps? More transparent but exposes implementation detail.
  • Stream the final stage character-by-character once earlier stages complete? Best UX but harder to build.

Most production systems land on option 3 — earlier stages run silently with a progress indicator ("Researching precedents…"), and the final stage streams. Worth deciding consciously rather than defaulting to whichever is easiest.

4. The four canonical topologies

Once you've answered the four design questions, you almost always land on one of four shapes. Each has a distinct feel and a distinct best-fit use case.

4.1 Supervisor-Worker

One coordinator dispatches sequenced sub-tasks to specialist agents and assembles their outputs into a final answer. This is by far the most common multi-agent pattern in production — roughly 70% of deployed multi-agent systems are some variant of it.

The mental model: the supervisor is a project manager. The workers are individual contributors with specific skills. The supervisor knows the shape of the work, hands off to the right specialist, validates what comes back, and chains it forward.

A key sub-decision: is the supervisor itself an LLM, or is it deterministic Python?

  • Deterministic supervisor: a Python function calls worker A, then B, then C, in that order, every time. Simple, fast, testable. Use when the workflow doesn't vary between requests.
  • LLM supervisor: a coordinator LLM decides which worker to call next based on the current state. Flexible, handles unanticipated routing, but adds latency, cost, and an LLM decision point to debug. Use when the workflow varies meaningfully.

Here's a deterministic supervisor — the simplest version, applied to the legal-research example from the opening:

EXTRACTOR_SYSTEM = """You are a legal document analyst. Given a document
excerpt, extract key facts. Output JSON: {"facts": [{"fact", "source", "relevance"}]}"""

RESEARCHER_SYSTEM = """You are a legal research specialist. Given case facts,
identify relevant precedents. Output JSON: {"precedents": [...]}"""

WRITER_SYSTEM = """You are a legal memo writer. Given facts + precedents,
draft a 3-5 paragraph memo with Background, Key Facts, Precedents, Analysis."""

def run_worker(system, user_message, model="claude-sonnet-4-6"):
    response = client.messages.create(
        model=model, max_tokens=2048, system=system,
        messages=[{"role": "user", "content": user_message}])
    return response.content[0].text

def run_pipeline(document):
    # The supervisor is plain Python here — no LLM.
    facts = json.loads(run_worker(EXTRACTOR_SYSTEM, f"Extract: {document}"))
    precedents = json.loads(run_worker(RESEARCHER_SYSTEM,
        f"Find precedents for: {json.dumps(facts)}"))
    memo = run_worker(WRITER_SYSTEM,
        f"Write memo. Facts: {json.dumps(facts)}\nPrecedents: {json.dumps(precedents)}")
    return memo

Three small things to notice in this code that matter at scale:

  • Each system prompt is short and focused. None of them have to do everyone else's job.
  • The handoffs are JSON. json.loads will throw on malformed output — that's failure isolation at the stage boundary. In production you'd catch the JSONDecodeError and retry just this stage with a schema-correction prompt.
  • The supervisor doesn't appear as an LLM call in this code. It's a Python function. Cheaper, faster, more testable than an LLM-routed version.

When you'd swap in an LLM supervisor: when the user's request type can't be classified upfront. ("Should I extract first, or do I need to summarize the document first because it's too long? Should I call the researcher twice with different sub-queries? Should I escalate to a human review?") A coordinator LLM can decide; deterministic Python cannot, without itself becoming a sprawling decision tree.

When supervisor-worker works: heterogeneous expertise the same model can't do well in one prompt, an auditable routing trail (regulated industries love this — "show me which agent made this decision"), and workflows where you want to swap one specialist without retesting the others.

When it doesn't: tasks that are inherently a single chain of thought (math problems, code generation for small functions) where breaking up the thinking loses more than it gains.

4.2 Typed Pipeline

A pipeline is supervisor-worker's deterministic case taken to its logical conclusion: a fixed linear sequence of stages, each receiving a typed object from the prior stage and emitting a typed object to the next. There's no LLM coordinator; there's a Python pipeline runner.

The difference from a casual three-call chain is the word typed. The handoffs use Pydantic schemas (or equivalent). Stage 2 will never receive malformed input from stage 1 because the schema validates at the boundary. If validation fails, you have a precise error message naming which field is broken — and you can retry just stage 1 with the schema error as feedback ("your output didn't include a 'relevance' field, valid values are 'high', 'medium', 'low'").

from pydantic import BaseModel, ValidationError
from typing import Literal

class Fact(BaseModel):
    fact: str
    source: str
    relevance: Literal["high", "medium", "low"]

class FactList(BaseModel):
    facts: list[Fact]

def extract_facts(document: str) -> FactList:
    raw = run_worker(EXTRACTOR_SYSTEM, f"Extract: {document}")
    try:
        return FactList.model_validate_json(raw)
    except ValidationError as e:
        # Retry once with the schema error as feedback
        feedback = f"Your output failed schema validation: {e}. Please fix and re-emit."
        raw = run_worker(EXTRACTOR_SYSTEM, f"{feedback}\n\nExtract: {document}")
        return FactList.model_validate_json(raw)

Why this matters more than it looks: without schemas, malformed intermediate output silently corrupts downstream stages and bugs surface only at the final user-visible artifact, miles from the root cause. Half the production multi-agent disasters in the field trace back to "we passed a freeform string between stages and stage 3 misinterpreted it."

Schemas also enable a clean failure model. Each stage either produces a valid typed object or raises. Retries can be precisely targeted. Logging captures structured intermediate state, not raw LLM text. Observability tools can show you the schema-validated artifact from any stage with one click.

The single most underrated practice in multi-agent engineering is using Pydantic (or JSON Schema, or Protobuf) for inter-stage handoffs. If a multi-agent system in a job interview has freeform string handoffs, the candidate is showing you their tutorial-grade understanding, not their production grade.

4.3 Debate

Debate is multi-agent built around the assumption that multiple perspectives surface more blind spots than one. N agents independently answer the same question from different framings, then critique each other's answers, then a synthesizer produces a final unified response.

The structure has three phases:

  1. Independent proposals. Each debater gets the same question with a different perspective prompt — "you are an analytical analyst," "you are a skeptical analyst," "you are a contrarian," "you are an empiricist who demands data." Answers are produced in parallel.
  2. Cross-critique. Each debater is shown the other proposals and asked to identify factual errors, logical gaps, and missing evidence.
  3. Synthesis. A final synthesizer integrates the proposals and critiques into a single well-reasoned answer.
def run_debate(question: str, n_debaters: int = 4) -> str:
    perspectives = ["analytical", "skeptical", "contrarian", "empirical"]

    # Phase 1: Independent proposals (parallel)
    proposals = [
        run_worker(f"You are a {p} analyst. Answer with evidence and reasoning.", question)
        for p in perspectives[:n_debaters]
    ]

    # Phase 2: Cross-critique
    critiques = []
    for i, proposal in enumerate(proposals):
        others = [p for j, p in enumerate(proposals) if j != i]
        critique = run_worker(
            "You are a rigorous critic. Identify factual errors, logical gaps, "
            "and missing evidence in the following proposal.",
            f"Proposal: {proposal}\n\nOther perspectives:\n{json.dumps(others)}")
        critiques.append(critique)

    # Phase 3: Synthesis
    return run_worker(
        "Integrate these proposals and critiques into a single well-reasoned answer.",
        f"Question: {question}\nProposals: {proposals}\nCritiques: {critiques}")

Debate's big risk: verbose-but-empty output. If the synthesizer prompt is weak ("pick the best answer"), the result is bland averaging — the synthesizer hedges and outputs something like "as the analytical perspective notes, X, while the skeptical perspective raises Y." This adds tokens without adding value.

The synthesizer's prompt is where debate either becomes powerful or becomes expensive theater. A strong rubric makes the difference:

"Identify which proposals contain claims contradicted by their cited evidence. Discard those claims. For remaining claims, weight by the strength of supporting evidence. Where proposals disagree on factual matters, side with the one citing authoritative sources. Where they disagree on judgment matters, present the stronger argument from each side."

That kind of synthesizer takes the diversity of debate and converges it into a sharper answer than any single perspective would have produced.

When to use debate: high-stakes decisions where blind spots matter more than latency — investment analysis, regulatory interpretation, medical second opinion, security threat modeling. Don't use debate for routine tasks; the latency and cost don't pencil.

4.4 Swarm (fan-out / fan-in)

The simplest multi-agent topology. You have N independent tasks and one worker function. You dispatch all N tasks in parallel, collect the results, and return.

import concurrent.futures
from typing import Callable

def run_swarm(tasks: list[str], worker_fn: Callable[[str], str],
              max_workers: int = 5) -> list[dict]:
    results = []
    with concurrent.futures.ThreadPoolExecutor(max_workers=max_workers) as ex:
        futures = {ex.submit(worker_fn, t): t for t in tasks}
        for future in concurrent.futures.as_completed(futures):
            task = futures[future]
            try:
                results.append({"task": task, "result": future.result(), "ok": True})
            except Exception as e:
                results.append({"task": task, "result": str(e), "ok": False})
    return results

There's no coordinator decision-making here. The "multi-agent" framing is generous — it's really one agent template applied N times in parallel. But the pattern shows up so often it's worth naming.

When swarm fits:

  • Summarize 1,000 customer reviews.
  • Translate 500 documents.
  • Classify every record in a batch.
  • Generate alt-text for 10,000 images.

What swarm requires:

  • Task independence. Worker N's output must not depend on worker M's output. If they do, you have a pipeline, not a swarm.
  • Rate-limit awareness. 1,000 parallel API calls will get you instantly rate-limited. max_workers should reflect your provider's actual concurrency limit, not the size of your task list.
  • Failure isolation. One failed worker shouldn't take down the batch. The example above wraps each future in a try/except so the batch returns partial success.
Subtle distinction: swarm vs LangGraph's "Send API." LangGraph's Send pattern spawns parallel branches whose results are merged via a reducer into a single state. That's structurally the same as swarm but adds graph-level reasoning about state merging. Both are fan-out/fan-in; LangGraph's version is more disciplined about how results recombine.

5. Variants worth knowing

The four canonical patterns above cover most production designs, but three variants come up often enough to be worth naming.

5.1 LLM-routed supervisor (dynamic handoff)

A supervisor-worker variant where the supervisor LLM decides which specialist to call based on the user's current question. This is what OpenAI's Agents SDK and Anthropic's swarm-style designs call handoffs. Use when intent classification is non-trivial — the user's request can plausibly need any of N specialists, and the routing rule is too complex to write as Python.

5.2 Hierarchical supervisor (supervisor of supervisors)

For very complex tasks, supervisors themselves can be specialists managed by a top-level supervisor. "Legal research supervisor" coordinates an extractor, researcher, and writer. "Financial analysis supervisor" coordinates its own team. A top-level coordinator routes the user's request to the right supervisor first, then that supervisor coordinates its workers. CrewAI's hierarchical process is exactly this.

5.3 Shared scratchpad

Some pipelines have agents share a free-form notes section that grows across stages. The extractor leaves a note like "couldn't find date for fact #3, check secondary source." The researcher reads the note and tries the secondary source. This is the messiest of the variants — easy to start, hard to scale, prone to context bloat. Useful when the inter-stage coordination is genuinely fuzzy and structured handoffs would lose nuance. Avoid as a default.

6. The plumbing nobody talks about

The conference talks focus on the topology diagrams. Production teams spend most of their time on the plumbing. Five things you'll build into every real multi-agent system:

6.1 Schema validation at every handoff

Covered above. The single highest-leverage piece of plumbing.

6.2 Idempotency keys

When stage 2 fails and you retry, you want the retry to be safe even if stage 2 actually succeeded but the success was lost in a network glitch. Each stage gets an idempotency key derived from the inputs (e.g., a hash of stage 1's output). If the downstream side (database write, external API) sees a duplicate idempotency key, it returns the cached result rather than re-executing. This is the same pattern Stripe uses for payments. In multi-agent systems with side effects (writing to databases, calling external tools that cost money), this is non-negotiable.

6.3 Retry with exponential backoff and a kill switch

Distinguish three failure classes and handle each differently:

  • Schema violation — retry the same stage with the validation error as feedback. Cap at 2 retries; if it can't produce valid output, escalate to a human or fall back to a degraded response.
  • Transient infra error (rate limit, 503) — retry with exponential backoff (1s, 2s, 4s, 8s). Cap at 4 retries.
  • Persistent failure — after retries exhausted, write the task to a dead-letter queue with all upstream context preserved. The task is re-runnable later without losing any earlier-stage work.

6.4 Tracing and observability

Every stage's input, output, latency, model version, and prompt version should be logged. Tools like LangSmith, LangFuse, Arize Phoenix make this turnkey. Without it, debugging a multi-agent system is opening N tabs in N consoles and correlating timestamps by hand.

6.5 Cost and rate-limit budgets

A multi-agent system can quietly consume 5–10× the tokens of its single-agent equivalent. You want per-request token budgets and per-tenant rate limits. When budgets are hit, the system should degrade gracefully (skip the optional verifier stage) rather than fail.

7. A production-grade walkthrough

To make the plumbing concrete, here's what a hardened version of the legal-research supervisor looks like — the same shape as the simple example earlier, but with the production discipline baked in:

from pydantic import BaseModel, ValidationError
import hashlib, time, logging

class Fact(BaseModel):
    fact: str; source: str; relevance: Literal["high","medium","low"]

class FactList(BaseModel):
    facts: list[Fact]

class Precedent(BaseModel):
    name: str; relevance: str; principle: str

class PrecedentList(BaseModel):
    precedents: list[Precedent]

class Memo(BaseModel):
    background: str; key_facts: str; precedents: str; analysis: str


def stage(name: str, system: str, user: str, schema: type[BaseModel],
          max_retries: int = 2) -> BaseModel:
    """Run one stage with schema validation, targeted retry, and tracing."""
    idempotency_key = hashlib.sha256(f"{name}:{user}".encode()).hexdigest()[:16]
    last_error = None

    for attempt in range(max_retries + 1):
        logging.info(f"stage={name} attempt={attempt} key={idempotency_key}")
        start = time.time()
        try:
            raw = run_worker(system, user)
            result = schema.model_validate_json(raw)
            logging.info(f"stage={name} OK latency_ms={int((time.time()-start)*1000)}")
            return result
        except ValidationError as e:
            last_error = e
            user = (f"Your previous output failed schema validation:\n{e}\n\n"
                    f"Please fix and re-emit. Original task:\n{user}")
        except Exception as e:
            # Transient — exponential backoff
            time.sleep(2 ** attempt)
            last_error = e

    raise RuntimeError(f"stage {name} failed after {max_retries} retries: {last_error}")


def run_pipeline(document: str) -> Memo:
    facts = stage("extractor", EXTRACTOR_SYSTEM, f"Extract: {document}", FactList)
    precedents = stage("researcher", RESEARCHER_SYSTEM,
                       f"Find precedents for: {facts.model_dump_json()}", PrecedentList)
    memo = stage("writer", WRITER_SYSTEM,
                 f"Write memo. Facts: {facts.model_dump_json()}\n"
                 f"Precedents: {precedents.model_dump_json()}", Memo)
    return memo

Read that code with the four design questions in mind:

  • Who decides what happens next? Python (deterministic). Three stages, fixed order.
  • How do agents share information? Typed handoffs. FactList → PrecedentList → Memo. No shared mutable state.
  • What happens when a stage fails? Schema failures retry with the validation error as feedback. Transient errors retry with backoff. Persistent failures raise — caller should catch and dead-letter.
  • What does the user see? The final Memo. Intermediate stages log but don't surface unless you wire them into a progress stream.

That's the shape every production-grade multi-agent system converges toward. The novel work is in the prompts and schemas; the orchestration code looks remarkably similar across teams.

8. The anti-patterns

Five things teams build into their multi-agent systems that they should stop doing.

8.1 Freeform string handoffs

"Stage 1 emits a paragraph, stage 2 reads the paragraph." Surfaces broken downstream output as final-user disasters. Always use typed handoffs.

8.2 The chatty supervisor

An LLM supervisor where every routing decision is a 1,500-token deliberation. Costs more than the actual work. Either make the supervisor deterministic Python or reduce it to a single classification call ("which specialist?") rather than open-ended reasoning.

8.3 Cargo-cult debate

Wrapping a routine task in a 4-debater + critique + synthesis loop because "more agents = more quality." For most tasks, you've added 5× cost and 3× latency for marginal quality improvement. Debate earns its cost only on high-stakes decisions where blind spots matter.

8.4 No idempotency

Side effects (database writes, external API calls) happen on every retry without an idempotency key. The first time a network blip retries a successful stage, you get double-writes and duplicate records.

8.5 The hidden 11th agent

A team adds agents one at a time. After six months the system has 11 LLM calls per user request. No one remembers exactly what agent 7 is doing or whether agents 4 and 9 are redundant. Periodic system audits — "can we collapse stages 3 and 4? does stage 7 still earn its cost?" — prevent this. Every agent in a production system should have a justified, named role.

9. Picking a topology — a decision framework

If you've gotten this far and still aren't sure which pattern fits your problem, work through these questions in order:

  1. Can you actually do this with a single agent? Try it first. If it works, ship it. Multi-agent is a tax — pay it only when you must.
  2. Are your tasks independent and parallel? If yes → Swarm. Done.
  3. Is the workflow the same shape every time? If yes → Typed Pipeline with deterministic Python orchestration.
  4. Does the workflow vary, but along a small set of known branches? If yes → Supervisor-Worker with a deterministic supervisor that picks one branch based on input features.
  5. Does the workflow vary unpredictably with the user's request? If yes → Supervisor-Worker with an LLM supervisor, accepting the latency and cost.
  6. Is this a high-stakes decision where blind spots are a known failure mode? If yes, and only then → consider Debate as a top-level wrapper.

Most production multi-agent systems are some flavor of #3 or #4. Debate (#6) is rare in well-run production but common in research papers. Swarm (#2) is extremely common but often dismissed as "not really multi-agent."

10. Interview takeaways

The senior framing condensed into one paragraph, ready for live delivery:

"I default to single-agent and escalate to multi-agent only when I can name the specific failure mode it solves — usually specialization sprawl or failure isolation, sometimes both. When I do go multi-agent, the first thing I decide is who controls flow: code, an LLM supervisor, or the agents themselves. That single choice determines whether I'm building a pipeline, a supervisor-worker, or a debate system. The plumbing — typed handoffs with schemas, per-stage retry semantics, idempotency keys, observability, cost budgets — matters more than the topology. Most production multi-agent failures I've debugged trace back to freeform string handoffs or missing failure isolation, not the wrong topology choice."

The three questions interviewers probe

"Walk me through what happens when stage 2 of your pipeline fails." Strong answer covers the three failure classes (schema, transient, persistent) and the distinct retry policy for each, plus what gets dead-lettered with what upstream context preserved.

"Why didn't you just use a single agent?" The honest answer names the failure mode multi-agent solved. "The single-agent system prompt was conflating extraction and writing tone — extraction needed comprehensive listing, writing needed selective synthesis, and the model averaged the two badly." Vague answers ("it was better") signal cargo-cult adoption.

"How do you decide whether to use an LLM as the supervisor?" Strong answer: cost and predictability. If the routing logic can be written in 20 lines of Python without becoming spaghetti, the deterministic supervisor wins. If it can't, the LLM supervisor earns its cost. The dimension that matters is workflow variance, not problem complexity.

The trap question

"How would you scale this multi-agent system to 100× traffic?" Junior answer: "add more workers." Senior answer: "Question whether the multi-agent design is still the right one at scale — many designs that win at 10 QPS lose at 1,000 QPS because the cumulative latency and cost shift the tradeoff. Specifically, I'd revisit whether the supervisor-worker pattern can be partially collapsed into a single agent with better prompting, whether some stages can be cached, whether the swarm stages can be batched into single API calls, and whether the debate pattern is still earning its cost or whether a single agent with a constitutional check is now sufficient. Scale forces re-examination of the topology, not just horizontal worker addition."
