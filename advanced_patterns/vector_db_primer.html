Vector Databases & RAG Internals

The concepts every AI Engineer is expected to be able to walk through in interviews — how vector databases really work, how they differ, and what's happening underneath the cosine similarity call.

Sections: 1. What a vector DB actually is 2. The three you'll meet 3. The four differentiating dimensions 4. HNSW deep dive 5. IVF for contrast 6. Quantization 7. Hybrid search 8. Where the chunks live 9. Picking a vector DB 10. Interview answer

1. What a vector DB actually is

Most introductions describe a vector database as "a database for cosine similarity search." That's roughly 30% of the truth and the part that misleads engineers into thinking these are simple kNN engines. The real picture:

What you THINK is stored:
{
    "id": "doc_42",
    "vector": [0.13, -0.87, ..., 0.04]
}

What's ACTUALLY stored:
{
    "id": "doc_42",
    "vector": [0.13, -0.87, ..., 0.04],
    "payload": {
        "doc_type": "legal_brief",
        "author": "smith_j",
        "date": "2025-03-14",
        "client_id": "acme_corp",
        "text": "The court held that..."   // ← chunk text often inline
    }
}

Every record is a vector + structured payload. The store maintains two coordinated indexes:

  1. Vector index (HNSW or IVF) for approximate nearest-neighbor cosine / dot-product search
  2. Attribute index (B-tree, hash, inverted index) for filtering on payload fields

A query like "find me the 10 most similar legal briefs from 2025, authored by Smith, for client Acme" hits both indexes and combines them. That hybrid is what makes vector DBs production-grade — they're specialized analytical stores optimized for "find similar AND attribute-matching," a job neither pure-relational nor pure-vector systems do well.

The cleanest mental model: a vector DB is half search engine, half relational store, with the two halves wired together by a smart query planner. The cosine-similarity side is largely commoditized across vendors — what differentiates them is the rest of the system.

2. The three you'll meet in production

Chroma · Qdrant · Pinecone. Each occupies a distinct position on the managed ↔ self-operated and embedded ↔ distributed axes.

ChromaDB

  • Open-source (Apache 2.0), Python + Rust
  • Embedded by default — runs in your Python process, persists locally to SQLite + Parquet. "SQLite for vectors."
  • Has a server mode but most usage is embedded
  • Strengths: zero ops, pip install and you have a working store in two lines
  • Weaknesses: awkward scaling story past ~1M vectors; embedded mode caps at one process

Qdrant

  • Open-source (Apache 2.0), written in Rust
  • Server-first client-server architecture from day one
  • Self-hostable (Docker / Kubernetes) or Qdrant Cloud
  • Strengths: rich filtering, native hybrid search, fast quantization (int8 + binary), mature Kubernetes operator, distributed sharding for horizontal scale
  • Weaknesses: operational overhead in self-host mode

Pinecone

  • Closed-source. Fully managed cloud service. No self-host option.
  • Serverless (default since 2024) — pay per request + storage, auto-scales
  • Strengths: zero ops, sub-50ms p99 across regions, enterprise SLAs, the "boring choice" for production at scale
  • Weaknesses: vendor lock-in, no offline/local-dev story, less feature-rich than Qdrant on filtering and hybrid search historically

Recruiters use these three as a rough proxy for experience level:

  2. Qdrant / Weaviate / pgvector — "I built a self-hosted vector store at scale." Signals you understand infra tradeoffs.

3. The four dimensions that distinguish them

3.1 Metadata filtering

The payload-filtering capability. The interesting design question is when the filtering happens relative to the vector search. Three strategies:

  • Pre-filter: narrow candidates by metadata predicate first, then run vector search on what's left. Wins on highly-selective filters. Loses when filter eliminates 99% of vectors and HNSW can't navigate the remainder.
  • Post-filter: vector search first, then drop non-matching candidates. Wins on low-selectivity filters. Loses when filter is selective — your top-K might all get dropped.
  • Integrated / single-stage: walks the HNSW graph while checking the payload filter at each step. Best of both worlds, hardest to implement. Qdrant is state-of-the-art here.

Why this matters in practice: MatchScout's Stage 1 does rule-based filtering in Python (location, budget, content_type) before Stage 2 cosine. A more sophisticated design would push that filter into the vector query as a payload predicate — one query instead of two stages. That's how production multi-tenant systems usually work.

3.2 Quantization

Compression of embedding vectors from float32 down to fewer bits to reduce memory + speed up search. Treated in depth in section 6.

3.3 Hybrid search (dense + sparse)

Running cosine on dense embeddings and BM25 on sparse keyword vectors in parallel, then combining the rankings via Reciprocal Rank Fusion. Treated in depth in section 7.

3.4 p99 latency

The 99th-percentile response time — 99% of queries finish faster than this number, 1% take longer.

You almost never quote the average in production engineering because it hides the tail. A system with 50ms p50 and 800ms p99 is a system where 1% of users have a terrible experience. Tail latency compounds in agentic systems: if your agent makes 5 vector calls per task, the probability of hitting at least one p99 call is 1 - (0.99)^5 ≈ 5% — one in 20 tasks has a slow step.

Vector DB latency rarely dominates the end-to-end agent — the LLM call that follows the retrieval is typically 10–100× more expensive. But tail latency matters for high-fan-out agents and real-time UX.

4. HNSW deep dive — how vector search actually works

Hierarchical Navigable Small Worlds. The dominant ANN algorithm. Used by Chroma, Qdrant, Weaviate, pgvector, Milvus, and (almost certainly) Pinecone serverless.

The problem it solves

You have N vectors, each D-dimensional. A query comes in. You want top-K nearest by cosine distance.

Brute force: O(N × D) per query.

  • 10K vectors × 1536 dims = 15M ops → ~5ms ✓
  • 10M vectors × 1536 dims = 15B ops → ~5 seconds ✗
  • 100M vectors × 1536 dims = 150B ops → minutes ✗

HNSW trades a tiny amount of recall (1–5% miss rate) for a massive speedup. At 1M vectors, it's roughly 200× faster than brute force. At 100M, 10,000× faster.

The storage representation — what's actually in memory

This is the part most explanations skip. An HNSW index is four data structures:

# 1. Vector storage — embeddings stored once, by ID
vectors = {
    "V1":  [0.13, -0.87, ..., 0.04],   # 1536-dim float array
    "V2":  [0.45,  0.21, ..., -0.11],
    ...
}

# 2. Layer assignment — which layers each vector lives on
max_layer = {
    "V1": 0, "V2": 0, "V6": 2, "V9": 1, "V12": 3, ...
}

# 3. Adjacency lists per layer — explicit neighbor IDs for each node
layer_0_neighbors = {
    "V1":  ["V2", "V4"],          # M neighbors per node at layer 0
    "V2":  ["V1", "V3", "V5", "V7"],
    "V8":  ["V7", "V9", "V3", "V14"],  # neighbors chosen by vector-space proximity,
    "V15": ["V14", "V16", "V11", "V22"],  # NOT by ID adjacency
    ...
}

layer_1_neighbors = { "V3": ["V6", "V9"], "V6": ["V3", "V9", "V12"], ... }
layer_2_neighbors = { "V6": ["V12"], "V12": ["V6", "V19"], ... }
layer_3_neighbors = { "V12": ["V19"], "V19": ["V12"] }

# 4. Single entry point
entry_point = "V12"

Important storage insight: the neighbors are not determined by ID adjacency. V15's neighbors at layer 0 could be [V8, V14, V21, V29] or anything else — they're whichever vectors the build process found closest to V15 in actual vector space. Visualizations that show vectors lined up in a row by ID are pedagogical conveniences; the real storage is adjacency lists.

The mental model — multiple resolutions of the same space

Each layer is a graph over the same vector pool but with different connectivity densities:

Layer 3 (top):    ●───────────────────●     (2 nodes, long sparse edges)
                  │                   │
Layer 2:          ●────●─────────●────●     (4 nodes, medium edges)
                  │    │         │    │
Layer 1:          ●──●─●──●──●───●──●─●     (8 nodes, more edges)
                  │  │ │  │  │   │  │ │
Layer 0:          ●●●●●●●●●●●●●●●●●●●●●     (ALL N nodes, dense edges)

The upper layers are NOT semantic categories or partitions. They're sparser graphs over the same space. A vector might exist on layers 0, 1, 2 (got lucky in random assignment) or only layer 0. There are no hard boundaries between regions — every layer covers the entire vector space.

Common misconception: "Layer 2 represents broad categories, layer 0 has the specific items." Wrong — that's a tree-based index (KD-tree, IVF). HNSW has no partitioning. The layers differ only in connectivity density; the navigation is graph traversal, not category narrowing.

The query algorithm

Three phases:

  1. Upper layers (greedy descent): from the entry point, repeatedly evaluate the current node's neighbors at this layer and jump to whichever is closest to query. Stop when no neighbor improves. Drop one layer, staying at the same vector.
  2. Layer 0 (priority queue, size ef_search): maintain a candidate pool. Pop the best unvisited candidate, evaluate its neighbors, update the pool. Continue until convergence.
  3. Return top-K from the layer-0 result set.

Worked example — three queries

With the 29-vector layout above (V12 and V19 at top layer; V8, V17, V25 as query targets):

Query targetWalkTotal evaluations
V8 (left)V12 → V12 → V6 → V9 → V8~10
V17 (middle)V12 → V19 → V19 → V16 → V17~7
V25 (right)V12 → V19 → V27 → V27 → V26 → V25~7

Same entry point (V12). Same graph. Same algorithm. The walks diverge immediately because at each step, "which neighbor is closest to Q?" gives a different answer depending on where Q is. No precomputed routing — greedy descent is what makes each query go in the right direction.

The two prices you pay

  1. 1–5% recall miss — greedy walk occasionally misses the true nearest neighbor. Mitigated by raising ef_search.
  2. Memory overhead — adjacency lists at each layer add 4–10% on top of raw vector storage.

5. IVF — the other algorithm, for contrast

Inverted File Index. The classic alternative to HNSW. Used by FAISS at billion-vector scale and as an option in Milvus.

The intuition

Cluster all vectors into K centroids (via k-means). Each vector belongs to its closest centroid. At query time, find the nprobe closest centroids to the query and brute-force-search only those buckets.

Step 1: Query vector q comes in.
Step 2: Compare q against ALL K centroids (K typically 1000-10000).
Step 3: Pick the nprobe closest centroids (typical nprobe = 8-32).
Step 4: Brute-force search vectors in those buckets only.
Step 5: Return top K by cosine.

This is what people often mistakenly think HNSW does. IVF really does partition space into regions and search within them. HNSW does not — that's the key distinction.

When IVF wins: billion-vector scale where memory matters more than recall ceiling, distributed systems where sharding-by-bucket is natural, and FAISS-style workloads with mostly-static data. Otherwise HNSW dominates.

6. Quantization — vector and LLM

Compression of float32 values to fewer bits. Same technique, two different targets.

The core idea

Embedding vectors are typically float32 — 4 bytes per dimension. A 1536-dim vector is 6,144 bytes. At 10M vectors, that's 61 GB. RAM becomes the bottleneck before anything else.

FormatBytes per dim1536-dim vector sizeRecall loss vs float32
float32 (baseline)46,144 B0%
float1623,072 B<1%
int811,536 B<1% (with re-ranking)
binary (1-bit)0.125192 B3–15% (with re-ranking)

Why quantization speeds up search (three effects, all real)

(1) Memory bandwidth is the dominant bottleneck. Modern CPUs do arithmetic far faster than they pull data from RAM. Cutting vector size 4× cuts the bytes you have to fetch 4× → roughly 4× faster end-to-end.

(2) Integer SIMD is faster than float SIMD. AVX-512 processes 16 float32 per instruction OR 64 int8 per instruction — 4× more parallelism.

(3) Binary changes the math entirely. For 1-bit vectors, cosine similarity becomes Hamming distance:

# Float cosine — expensive
similarity = sum(a[i] * b[i] for i in range(D)) / (|a| * |b|)
# 1500 multiply-adds for a 1536-dim vector

# Binary "similarity" — Hamming distance via XOR + popcount
distance = popcount(a XOR b)
# 24 XOR + popcount instructions for the same 1536 dims
# 10-40× faster in practice

Re-ranking — the trick that preserves accuracy

Production systems do two-stage search:

  1. Stage 1: scan ALL quantized vectors super fast, pull top 100 candidates
  2. Stage 2: re-rank those 100 with full-precision float32 vectors

You get binary-quantization speed for the bulk filter and float32 accuracy for the final ranking. Recall loss drops to under 1% even with binary.

The same idea for LLMs

When you ran Gemma 4 26B Q4_K_M on the home GPU box, you were doing the exact same math applied to a different object:

LLM weight quantizationVector DB quantization
What gets compressedModel weightsEmbedding vectors
Original formatfloat32 / float16float32
Common targetsint8, int4, NF4, Q4_K_Mint8, binary, PQ
The mathscale + zero-point mappingscale + zero-point mapping
Why it speeds upMemory bandwidth + SIMDMemory bandwidth + SIMD
Quality tradeoffPerplexity goes upRecall@K goes down

Q4_K_M means most weights at 4 bits, some critical layers at higher precision — directly analogous to vector DB binary scan + float re-rank.

The unification worth carrying into interviews: "Quantization in modern AI infrastructure is one technique — map floats to fewer-bit integers via scale + zero-point — applied wherever memory bandwidth dominates over arithmetic precision. LLM inference uses it for weights. Vector databases use it for embeddings. Both pay a small accuracy tax for a large speed and memory gain. The fact that both communities converged on 8× compression with <1% loss at int8 isn't coincidence — it's because the underlying bottleneck is the same."

7. Hybrid search — dense + sparse

Pure cosine on dense embeddings is great at semantic matching but bad at exact-token retrieval — error codes, function names, drug names, citation strings. The embedding model has likely never seen the rare token, so cosine distance is no better than random for documents containing it.

Sparse retrieval (BM25, TF-IDF) is the opposite — nails exact-token matching, misses paraphrase. Hybrid search runs both and combines.

BM25 in one sentence

BM25 tokenizes the query and each document, scores documents by how much the query's tokens appear in them, weighted by rarity (rare tokens like EADDRINUSE get higher weight than common ones like "the"). It's a bag-of-words model. It does not understand paraphrase — port already in use and EADDRINUSE share zero tokens, so BM25 sees zero overlap.

The four-cell coverage map

Query has rare tokenQuery is paraphrased
Doc has rare tokenBM25 winsDense wins (semantic bridge)
Doc has paraphraseDense wins (if model knows it)BM25 wins (literal match)
Doc has neitherNothing finds it

In three of four cells, hybrid genuinely adds value over either alone. Hybrid search is not "BM25 catches exact, dense catches semantic" — both methods match on tokens, just different kinds. Hybrid wins because dense and sparse succeed in different parts of the query × document space, and combining them covers more ground than either alone.

Reciprocal Rank Fusion (RRF) — the combination algorithm

dense_results  = vector_search(query)   # top 20 with ranks
sparse_results = bm25_search(query)     # top 20 with ranks

# RRF score for each doc:
score(doc) = sum over each retriever of 1 / (k + rank_in_that_retriever)
# k is typically 60

# Docs that rank highly in BOTH win.

Production reality: hybrid search beats pure-dense on most retrieval benchmarks by 5–15% recall@10, especially on technical content (code, error logs, scientific papers, legal docs). It's the default in modern production RAG.

8. Where the actual chunk text lives

Crucial question that "how does RAG work" diagrams gloss over. The LLM doesn't see vectors. It sees text chunks. Where are those chunks?

Architecture A — chunks stored INSIDE the vector DB (the default)

{
    "id": "doc_42_chunk_7",
    "vector": [0.13, -0.87, ..., 0.04],
    "payload": {
        "text": "The court held that the doctrine of fair use applies when...",
        "doc_id": "doc_42",
        "page_number": 17,
        "source_url": "https://..."
    }
}

One round trip, simple architecture. This is what P2 DocTalk does — when you call collection.query(...), returned chunks come from the payload.

Architecture B — chunks stored EXTERNALLY, only an ID in the vector DB

# In the vector DB:
{
    "id": "doc_42_chunk_7",
    "vector": [0.13, -0.87, ..., 0.04],
    "payload": {
        "external_ref": "s3://my-bucket/docs/doc_42/chunk_7.txt",
        "doc_id": "doc_42",
        "page_number": 17
    }
}

# Query path:
top_ids = vector_db.query(query_vector, top_k=10)
chunks  = [s3.get(r.payload["external_ref"]) for r in top_ids]

Two round trips but the vector store stays lean. Used at large scale where storing inline is too expensive. Pinecone charges by storage volume in serverless, so this pattern is common there.

Most production systems pick inline. The 5–10× storage cost is dwarfed by simplicity gains at <100M chunks. External storage shows up at extreme scale or when chunk text has a different lifecycle (e.g., updated independently of embeddings).

9. Picking a vector DB — decision framework

Pick ChromaDB when…

  • Prototyping, tutorials, personal RAG projects
  • Under 1M vectors, single-process access
  • You don't want to operate anything
  • You're early enough that the vector store doesn't have to be the production choice
  • Local semantic caches — exactly this profile: small, embedded, low-ops

Pick Qdrant when…

  • Going to production with ops capability and want self-host flexibility
  • Need rich filtering — payload-predicate queries that are first-class
  • Need hybrid search without bolting on a second system
  • Scale-conscious — quantization (int8, binary) cuts memory 4–32×
  • Concerned about vendor lock-in or per-request pricing
  • Want a production-grade store you can also run on a laptop — Qdrant uniquely wins here

Pick Pinecone when…

  • Need managed vector DB and "we'll just operate it" isn't acceptable
  • Need enterprise SLAs, audit logs, contracts — Pinecone has a sales team; the others have GitHub issues
  • Bursty traffic where serverless economics work in your favor
  • You explicitly want vendor lock-in because the managed simplicity is worth it (legitimate choice)
  • Recruiter signal — shows up in JDs more than the other two combined

10. The 90-second interview answer

"A vector database is half search engine, half relational store. It maintains a vector index for approximate nearest-neighbor search and an attribute index for filtering on structured payload, with a query planner combining them. The cosine-similarity side is largely commoditized — the real differentiation is in metadata filtering, quantization, and hybrid search.

The dominant indexing algorithm is HNSW, which builds a multi-layer graph where each layer is the same vector pool with a different connectivity density — sparser edges higher up for long-range jumps, denser at layer 0 for fine-grained search. A query does greedy descent through the upper layers and then a priority-queue search at layer 0. The whole thing reduces query work from O(N) brute force to roughly O(log N + ef_search × M), which is a ~200× speedup at 1M vectors and 10,000× at 100M, in exchange for 1–5% recall loss and ~5% memory overhead.

The alternative algorithm, IVF, partitions space into k-means buckets and probes a few — that's the one people often think HNSW does. IVF wins at extreme scale and natural sharding; HNSW wins everywhere else.

Quantization compresses vectors from float32 down to int8 or binary, cutting memory 4–32× and speeding queries 2–40× via memory bandwidth gains and SIMD parallelism. Combined with a re-ranking pass on the top-K candidates, recall loss stays under 1% even with binary. The exact same math is what compresses LLM weights to Q4_K_M for local inference — it's one technique applied to different objects.

Hybrid search combines dense embedding retrieval with sparse BM25 keyword retrieval via Reciprocal Rank Fusion. It wins on technical content where exact-token matches matter — error codes, drug names, code identifiers — which dense embeddings handle poorly.

Chroma, Qdrant, Pinecone — the three production choices. Chroma is SQLite for vectors, embedded and zero-ops, prototyping default. Qdrant is open-source Rust, server-first, strongest on filtering and quantization, self-host or managed. Pinecone is closed-source SaaS, zero-ops, vendor lock-in, the enterprise default. Pick depends on whether you want to operate it, pay someone else to operate it, or it's small enough not to need operating."
