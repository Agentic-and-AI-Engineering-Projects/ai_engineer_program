1. What Bedrock actually is

AWS Bedrock is a thin AWS wrapper around third-party foundation models — Anthropic's Claude, Meta's Llama, AI21's Jamba, Cohere's Command, plus Amazon's own Titan and Nova lines. The model weights live on AWS infrastructure; you call them through a standard AWS SDK pattern with IAM authentication.

It's not a model. It's an access layer. Same Claude weights, AWS-hosted deployment, AWS-billed, AWS-IAM-controlled.

The cleanest one-liner: Bedrock = "all your favorite foundation models, but routed through AWS so they fit inside your existing AWS security perimeter, billing, and audit trail."

2. Same model, multiple hosts

Claude is deployed in multiple places. The weights are the same; the infrastructure isn't.

It's a B2B distribution deal: Anthropic gives AWS the model weights and gets paid through Bedrock revenue share. When you call Bedrock, your request never touches Anthropic's network — it stays inside AWS the entire time.

3. Why enterprises pick Bedrock

For a solo developer prototyping: direct API is simpler — one key, one provider, done.

For an enterprise: Bedrock wins because AWS is already the trust boundary. The CISO has already approved AWS for sensitive data; adding Anthropic as a separate vendor means:

  • Separate procurement cycle
  • Separate security review (SOC 2 attestation, data-processing agreement)
  • Separate audit logs (Anthropic's vs your CloudTrail)
  • Separate billing reconciliation
  • Separate quota and credential rotation

Routing Claude through Bedrock collapses all of that into "it's just another AWS service." That's the entire reason Bedrock exists. Anthropic gets enterprise distribution they couldn't easily build themselves; AWS gets to claim "we have Claude" in their pitch; enterprises get one bill and one compliance perimeter.

Interview signal: "I built X on Bedrock" lands harder than "I called the Anthropic API" because it signals you can navigate IAM + AWS billing + compliance plumbing — the boring infrastructure work that separates a prototype from a production system.

4. boto3 fundamentals

boto3 is the official AWS SDK for Python. Think of it as "what anthropic is to api.anthropic.com, what openai is to api.openai.com — boto3 is to AWS." But AWS has 200+ services, so boto3 is structured as a per-service client.

The basic pattern

import boto3

# 1. Create a client for a specific AWS service
s3 = boto3.client("s3")

# 2. Call methods that map 1:1 to that service's REST API actions
buckets = s3.list_buckets()
s3.put_object(Bucket="mybucket", Key="foo.txt", Body=b"hello")

Every AWS service follows this same shape. Just swap the service name:

ec2 = boto3.client("ec2");           ec2.describe_instances()
dynamodb = boto3.client("dynamodb"); dynamodb.put_item(...)
bedrock = boto3.client("bedrock");   bedrock.list_foundation_models()

Method names always match AWS API actions in snake_case. AWS docs say ListFoundationModels, boto3 method is list_foundation_models. Navigating any AWS service in Python becomes mechanical once you know this pattern.

How auth works — the credentials chain

You never pass credentials in code. boto3 looks for them automatically in this order:

  1. Environment variables — AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION
  2. ~/.aws/credentials file — what aws configure writes to
  3. ~/.aws/config file — for profiles, SSO, region defaults
  4. IAM role — if running on EC2 / Lambda / ECS / EKS, the attached role's temporary credentials
  5. Container credentials — for ECS task roles
  6. EC2 instance metadata — fallback for EC2

First match wins. For the P2.5 primer, boto3 reads ~/.aws/credentials because you ran aws configure. Zero credential code needed in the script.

Region matters

AWS services are regional. The same boto3 client pointed at us-east-1 and eu-west-1 talks to two completely different infrastructures (different S3 buckets, different Bedrock models available, different latency, different prices).

boto3.client("bedrock", region_name="us-east-1")    # per-client (explicit, recommended)
# OR
export AWS_REGION=us-east-1                          # env var
# OR
# ~/.aws/config:  [default] region = us-east-1

Two clients for Bedrock — control plane vs data plane

ClientRoleCommon calls
boto3.client("bedrock")Control planelist_foundation_models, list_inference_profiles, describe_*
boto3.client("bedrock-runtime")Data planeinvoke_model, invoke_model_with_response_stream

AWS splits "management" from "data" across many services. You need both for Bedrock: bedrock to discover models, bedrock-runtime to actually call them.

5. Three ways to call Claude

This is the conceptual pivot most engineers miss. There are three distinct access paths, each with different auth and different code:

What you writePathAuth
anthropic.Anthropic()Direct Anthropic APIANTHROPIC_API_KEY env var
boto3.client("bedrock-runtime")Raw Bedrock (what our primer uses)AWS IAM credentials
anthropic.AnthropicBedrock()Anthropic SDK pointing at BedrockAWS IAM credentials

The third option deserves explanation

The Anthropic SDK ships a Bedrock-flavored client (AnthropicBedrock) that uses the same Messages API surface as anthropic.Anthropic() but routes through Bedrock under the hood. No ANTHROPIC_API_KEY needed:

from anthropic import AnthropicBedrock

client = AnthropicBedrock(
    aws_region="us-east-1"
    # AWS credentials auto-resolved from ~/.aws/credentials, env vars, IAM role
)

response = client.messages.create(
    model="anthropic.claude-sonnet-4-6",
    max_tokens=256,
    messages=[{"role": "user", "content": "Hello"}],
)
print(response.content[0].text)

Internally it builds the AWS-signed request, adds the anthropic_version: bedrock-2023-05-31 envelope, parses the response — exactly what raw boto3 does, but hidden behind a clean interface. Drop-in swap for production code that currently uses anthropic.Anthropic().

When to use which

Use casePick
Dev / personal projects, Anthropic-onlyanthropic.Anthropic() (direct)
Enterprise / production / multi-provider stackAnthropicBedrock() or raw boto3
Quick AWS API understanding / wire-format demoRaw boto3.client("bedrock-runtime")
Drop-in swap from direct API → Bedrock with minimal code changeAnthropicBedrock()

6. The invoke flow

Raw boto3 invocation, line by line:

import json
import boto3

runtime = boto3.client("bedrock-runtime", region_name="us-east-1")

request_body = {
    "anthropic_version": "bedrock-2023-05-31",   # required envelope marker
    "max_tokens": 256,
    "messages": [{"role": "user", "content": "Hello"}],
}

response = runtime.invoke_model(
    modelId="anthropic.claude-sonnet-4-6",
    body=json.dumps(request_body).encode("utf-8"),
    contentType="application/json",
    accept="application/json",
)

# Response body is a streaming object — read it once
body = json.loads(response["body"].read())

print(body["content"][0]["text"])
print(f"Tokens: in={body['usage']['input_tokens']} out={body['usage']['output_tokens']}")

Key details

  • anthropic_version: bedrock-2023-05-31 — required by Bedrock. It's an envelope marker letting the same invoke_model method serve multiple model families. Without it, Bedrock can't route the body to the right adapter.
  • Body is bytes, not a dict — must JSON-encode and UTF-8 encode before sending.
  • Response body is a stream — call .read() once to consume it; calling it again yields an empty buffer.
  • Everything inside the body (except anthropic_version) is the same Anthropic Messages API you already know — same messages shape, same max_tokens, same response structure. Bedrock just wraps it.

For streaming responses

response = runtime.invoke_model_with_response_stream(
    modelId="anthropic.claude-sonnet-4-6",
    body=json.dumps(request_body).encode("utf-8"),
)

for event in response["body"]:
    chunk = json.loads(event["chunk"]["bytes"])
    if chunk["type"] == "content_block_delta":
        print(chunk["delta"]["text"], end="", flush=True)

7. Model IDs & inference profiles

Bedrock has two flavors of model identifier:

TypeExampleBehavior
Plain region-pinned IDanthropic.claude-sonnet-4-6Runs in your client's region. Single-region quota.
Cross-region inference profileus.anthropic.claude-sonnet-4-6Bedrock routes the call across multiple US regions transparently. 2-3× higher effective rate limits at no cost difference.

To see what's available in your account:

# List all Claude models in your region
aws bedrock list-foundation-models \
    --region us-east-1 \
    --query "modelSummaries[?providerName=='Anthropic'].[modelId,modelName]" \
    --output table

# List all cross-region inference profiles
aws bedrock list-inference-profiles --region us-east-1

Production almost always uses cross-region. The us. prefix gets you 2-3× more throughput for the same workload, with better tail-latency resilience (one region's outage doesn't kill the call). Pricing is identical.

8. Setup checklist

What it takes to go from "no AWS account" to "running the P2.5 primer." Roughly 10-15 minutes if you don't have an AWS account; 5 minutes if you do.

One-time setup

  1. AWS account — Sign up at https://aws.amazon.com if you don't have one. Free tier covers our exercise (Bedrock has no free tier, but our spend is pennies).
  2. IAM user with AdministratorAccess — In the IAM console: Users → Create user → attach AdministratorAccess policy. Recommended over root user keys per AWS best practice.
  3. Access keys for that user — User → Security credentials → Create access key → CLI use case → download the CSV. Keys look like AKIA... (access key) and a 40-char secret. Never commit these or paste into chat.
  4. Configure AWS CLI: 
    aws configure
# AWS Access Key ID: AKIA...
# AWS Secret Access Key: (the secret)
# Default region: us-east-1
# Default output format: json
  5. Install boto3: pip install boto3
  6. Verify: aws sts get-caller-identity should print your account ID + IAM user ARN.

Model access (recent change — auto-enabled)

As of 2026, AWS retired the explicit "Model Access" page. Serverless foundation models auto-enable on first invocation in any AWS commercial region. For Anthropic models specifically, first-time users may see a use-case form before the first invoke succeeds.

If you hit AccessDeniedException on the first invoke, navigate to Bedrock Console → Model catalog → click the Claude model → fill in the use-case form (typical answers: "internal R&D / developer prototype"). Approval is usually instant for Anthropic models in US regions.

9. Pricing reality

The good news for the curriculum: Bedrock costs pennies for our exercises.

Claude Sonnet 4.6 pricing (approx)Cost
Per million input tokens~$3.00
Per million output tokens~$15.00
P2.5 primer single test call (~20 in, ~50 out)~$0.0008
P13 full MatchScout V2 build on Bedrock (estimated)$5–20 total

Bedrock charges the same per-token rate as direct Anthropic API. No Bedrock surcharge. You're paying for AWS-side conveniences (IAM, billing rollup, audit logs), not for the model access itself.

AWS does NOT offer a Bedrock free tier currently (different from EC2/S3 free tier). It's pay-per-use from request #1, but the per-call cost is tiny.

Set a budget alarm anyway (3 minutes, free): https://console.aws.amazon.com/billing/home → Budgets → Create budget → set monthly threshold like $20 → email alert at 80%. Catches surprises before they become bills.

Cost tracking pattern (reuse from P7 MatchScout)

input_tokens  = response_body["usage"]["input_tokens"]
output_tokens = response_body["usage"]["output_tokens"]

cost_usd = (
    input_tokens  * 3.00  / 1_000_000
    + output_tokens * 15.00 / 1_000_000
)

# Persist cost_usd on every call → aggregate by tenant, model, prompt version

Same pattern P7 MatchScout uses with the cost_usd column. Per-call cost persistence is the foundation of all production cost discipline — alerts, per-tenant budgets, prompt-version cost A/Bs all build on this.

10. Common errors

All Bedrock errors raise botocore.exceptions.ClientError. The interesting detail is in e.response["Error"]:

from botocore.exceptions import ClientError

try:
    runtime.invoke_model(modelId="anthropic.claude-sonnet-4-6", body=...)
except ClientError as e:
    code = e.response["Error"]["Code"]        # e.g. "AccessDeniedException"
    msg = e.response["Error"]["Message"]      # human-readable
    print(f"{code}: {msg}")
Error codeTypical causeFix
AccessDeniedExceptionModel access not yet granted, OR IAM policy missingVisit Bedrock console → Model catalog → request access; or attach bedrock:InvokeModel to IAM
ResourceNotFoundExceptionWrong model ID or wrong regionVerify model ID with aws bedrock list-foundation-models; confirm region matches
ValidationExceptionMalformed request body (missing anthropic_version, wrong message shape, etc.)Read the error message — it's usually specific
ThrottlingExceptionHit rate limit on the modelRetry with exponential backoff; for production, switch to cross-region inference profile
ServiceQuotaExceededExceptionAccount-level quota hitRequest quota increase in Service Quotas console
UnrecognizedClientExceptionBad AWS credentialsaws sts get-caller-identity to diagnose

Key observations from the run:

  • Cost per-token is genuinely identical between paths — the tiny difference ($0.000015) is just because Direct Anthropic returned one extra output token. Confirms the "pricing parity" claim empirically.
  • Bedrock was 20% FASTER than direct Anthropic on this run (12.2s vs 15.2s). This isn't universal — it's one sample and depends on network routing, cache state, and the direct-API endpoint's regional traffic. But it kills the assumption that direct-API is always faster. In practice, Bedrock latency is competitive because AWS runs the model on infrastructure close to your workload.
  • Output text was nearly identical semantically — different phrasing (Bedrock: "specialized database system designed to store, manage, and index" vs. Direct: "specialized database designed to store, index, and query"), same technical content, same length within 1 token. Confirms both paths hit the same weights.

What the model discovery call revealed

The account's list_foundation_models + list_inference_profiles calls returned:

  • 17 foundation models visible (all Claude generations from 3 through Sonnet 5 and Opus 4.8)
  • 65+ cross-region inference profiles across Anthropic, Meta Llama, DeepSeek, Amazon Nova, Mistral, Stability, Writer, TwelveLabs, Cohere
  • Two prefix flavors: us.* (routes across US regions only) and global.* (routes worldwide; newer, higher throughput ceiling)
The lesson worth carrying forward: Bedrock progressively deprecates on-demand invocation of plain region-pinned IDs for newer models. The first run of the primer with anthropic.claude-sonnet-4-6 hit ValidationException: Invocation of model ID ... with on-demand throughput isn't supported. Fixing it was one string change: add the us. prefix. Default new code to cross-region profile IDs — same code path, higher rate limits, futureproof.

11. The 90-second interview answer

"AWS Bedrock is a thin AWS access layer over third-party foundation models — Claude, Llama, Cohere, plus Amazon's own. Same model weights as the direct Anthropic API, different deployment: the model runs on AWS infrastructure, authenticated via IAM, billed through AWS, audited through CloudTrail. The reason enterprises pick Bedrock over the direct API isn't performance or pricing — pricing is per-token-equivalent — it's the trust boundary. AWS is already approved by the CISO; adding Claude through Bedrock means one bill, one compliance perimeter, one IAM model.

You access Bedrock through boto3 with two clients: bedrock for control-plane operations like listing models, and bedrock-runtime for actually invoking them. The invoke flow uses invoke_model(modelId, body) where the body is the standard Anthropic Messages API wrapped in a Bedrock envelope (anthropic_version: bedrock-2023-05-31). There are three ways to call Claude in practice: anthropic.Anthropic() for direct API, boto3.client('bedrock-runtime') for raw Bedrock, or anthropic.AnthropicBedrock() which is the Anthropic SDK pointing at Bedrock — same Messages API, AWS credentials underneath. For production-grade code I'd pick AnthropicBedrock; for understanding the wire format, raw boto3.

Model IDs come in two flavors: region-pinned (anthropic.claude-sonnet-4-6) and cross-region inference profiles (us.anthropic.claude-sonnet-4-6) that route across multiple AWS regions for 2-3× higher rate limits at no cost difference — production should default to cross-region. Common failure modes are AccessDeniedException (model access not granted), ResourceNotFoundException (wrong model ID or region), and ThrottlingException (hit rate limit). Pricing matches direct Anthropic per-token; the value-add is the AWS infrastructure wrapping, not a different model."
