Kafka Primer for Agentic Systems

What every senior agent engineer needs to know about Kafka without becoming a streaming infra specialist. Anchored to p3_researchbot/kafka_agents.py — the Agent-as-Kafka-Consumer pattern.

Sections: 1. Why an agent on Kafka 2. The mental model 3. group_id 4. Offsets & auto-commit 5. Delivery semantics 6. Partitions in depth 7. Pinning consumers to partitions 8. The pattern 9. Kafka vs alternatives 10. Production gotchas 11. Interview answer

1. Why put an agent behind Kafka at all?

In-process orchestrators (LangGraph, CrewAI) work great for one request, one process. They fall over once you need:

  • Crash recovery — if the orchestrator dies mid-loop, partially-done work is lost
  • Horizontal scale — one process can't keep up with bursts of requests
  • Decoupled components — the team that owns intake shouldn't be coupled to the team that owns the model call
  • Replay — re-process the last 24 hours of inputs through a new prompt version without re-collecting the inputs
  • Audit — regulators want a durable record of every prompt the system ever saw

Kafka gives you a durable, replay-able, partitioned commit log that decouples producers from consumers. Agents become long-running consumers on the log.

One-liner: Kafka turns the agent loop from "in-memory pipeline crashing on one bad input" into "durable event stream that any number of agent workers consume independently, can replay, and can scale horizontally without code changes."

3. group_id — the single most important concept

Kafka tracks the read position per (group_id, topic, partition) tuple. The same broker holds many independent positions:

Internal "where am I" table:
  ('news-group',       'research-tasks',    partition=0) → offset 42
  ('technical-group',  'research-tasks',    partition=0) → offset 42
  ('examples-group',   'research-tasks',    partition=0) → offset 42
  ('aggregator-group', 'research-findings', partition=0) → offset 17

Two patterns you're choosing between

Pattern A — Different group_id per consumer → broadcast / fan-out

What kafka_agents.py does. Each group is an independent reader; every group sees every message.

consumer('news')       # group_id='news-group'       sees ALL 3 tasks
consumer('technical')  # group_id='technical-group'  sees ALL 3 tasks
consumer('examples')   # group_id='examples-group'   sees ALL 3 tasks
                       # each filters by task['agent'] == agent_type

Pattern B — Same group_id across N consumers → queue / load balancing

Run the same consumer process 3 times with the same group_id; Kafka assigns each partition to exactly one of them. Each message goes to exactly one consumer. This is how you horizontally scale a single agent type.

KafkaConsumer('research-tasks', group_id='news-group')  # worker 1
KafkaConsumer('research-tasks', group_id='news-group')  # worker 2
KafkaConsumer('research-tasks', group_id='news-group')  # worker 3
                                # 3 partitions → 1 per worker
                                # each task processed by exactly 1 worker

4. Offsets and commit semantics

The offset is the message position. Every message in a partition gets a strictly-increasing offset (0, 1, 2, ...). A consumer says "I've finished processing up to offset N" by committing that offset to Kafka. On restart, the consumer resumes from the committed offset.

"Where is the commit?" — auto-commit is the answer

In kafka_agents.py there is no explicit c.commit() call. The KafkaConsumer constructor defaults to two parameters that drive a background commit thread:

ParameterDefaultMeaning
enable_auto_commitTrueBackground thread commits offsets on a timer
auto_commit_interval_ms5000The interval — every 5 seconds

So in code with these defaults, every 5 seconds the client silently tells the broker "I've processed up to offset N," without you writing any commit code.

The auto-commit trap — silently weaker than at-least-once. 
for msg in c:                       # consumer reads message at offset 42
    task = msg.value
    # 5 seconds tick by. Auto-commit fires in the background.
    # Broker now thinks offset 42 is "done".

    findings = ddgs.text(...)       # but you're still processing
    # CRASH HERE

    p.send(FINDINGS_TOPIC, ...)     # finding never published
On restart: last committed offset = 42 → consumer picks up at offset 43 → offset 42's work is lost. This is at-most-once behavior, dressed up as at-least-once. The bug is invisible until it bites you.

Manual commit (production discipline)

c = KafkaConsumer(..., enable_auto_commit=False)   # disable the timer
for msg in c:
    result = process(msg)             # do the work
    publish_result(result)             # side effect succeeds
    c.commit()                         # only now mark as done

Commit after the side effect succeeds. If you crash before commit, the message is redelivered on restart — losing nothing but doing duplicate work. This is true at-least-once delivery. Combine it with an idempotent processor (dedupe by a stable key) and you get effectively-exactly-once results.

Senior framing: "At-least-once" is the contract Kafka gives you when you commit correctly. With default auto-commit, you don't get that contract — you get a race between processing time and the 5-second commit timer. The first thing to do on a production consumer is set enable_auto_commit=False and call commit() after every successful piece of work.

auto_offset_reset — the "fresh group" gotcha

When a group_id is brand new (Kafka has never seen it before, has no committed offset), it has to decide where to start. That's what auto_offset_reset controls:

  • 'earliest' — start from the very first message in the topic. Great for demos and replay.
  • 'latest' (default) — only see messages produced after you joined. What production usually wants.

Once the group has committed even one offset, auto_offset_reset never fires again — Kafka resumes from the committed position.

This is also how you replay: pick a brand-new group_id + 'earliest', and you re-read the entire topic from the start. No data movement, no exports. The reason ML teams love Kafka — re-evaluate every input under a new prompt by spinning up a new consumer group.

5. Delivery semantics — the three guarantees

GuaranteeHow you get itWhat you give up
At-most-once Commit before processing. Crash → message lost. Reliability (you may lose work)
At-least-once Commit after processing. Crash → message reprocessed. Idempotence required (your processor must tolerate duplicates)
Exactly-once Kafka transactions: produce+commit in one atomic step (idempotent producer + transactional consumer). Complexity + ~10-30% throughput hit

For agent systems, at-least-once is almost always the right choice. LLM calls are expensive but idempotent if you key your work properly (use the message offset or a deterministic task_id as the cache key, dedupe outputs by that key downstream).

Practical pattern: at-least-once delivery + idempotent processing = effectively exactly-once results, without paying the transactional throughput tax. This is what production agent systems actually run.

6. Partitions in depth

A topic is not a single log file — it is an abstraction over N parallel log files called partitions. Each partition is its own append-only log with its own offset counter.

Topic "research-tasks" with 3 partitions:

  partition 0:  [msg0] [msg1] [msg2] [msg3] [msg4]   →  offsets 0, 1, 2, 3, 4
  partition 1:  [msg0] [msg1] [msg2]                 →  offsets 0, 1, 2
  partition 2:  [msg0] [msg1] [msg2] [msg3]          →  offsets 0, 1, 2, 3
  • Each partition has its own offset counter starting at 0. Offset 0 in partition 0 is a different message from offset 0 in partition 1.
  • A "topic" doesn't physically exist — only its partitions do. The topic is a logical grouping name.
  • Messages are spread across partitions by the producer.

The ordering guarantee

Messages are strictly ordered within a partition. There is no ordering guarantee across partitions.

This is partition-scoped, not topic-scoped, not group-scoped. Inside one partition, offsets 0 → 1 → 2 → 3 are read in strict order by every consumer. Across partitions, a message in partition 0 at offset 5 may have been produced before a message in partition 1 at offset 2, yet a consumer reading both may see partition 1's message first. Coordinating a global order would defeat the entire point of partitioning.

How the producer assigns a message to a partition — card dealer vs. assigned seating

Case A — no key: round-robin (card dealer)

p.send('research-tasks', value=msg)   # no key
# Kafka cycles through partitions in order:
#   msg1 → partition 0    msg5 → partition 0
#   msg2 → partition 1    msg6 → partition 1
#   msg3 → partition 2    msg7 → partition 2
#   msg4 → partition 3    msg8 → partition 3

Even distribution, predictable. But ordering is lost — msg5 may be processed by a different consumer than msg1 even though the producer sent them in that order.

Case B — with key: hash(key) % N (assigned seating)

p.send('research-tasks', key='user_42'.encode(), value=msg)
# Kafka computes partition = hash('user_42') % num_partitions
# user_42's messages ALWAYS go to the same partition.

  msg1 (user_42)  → hash → partition 2
  msg2 (user_07)  → hash → partition 0
  msg3 (user_42)  → hash → partition 2     ← always here
  msg4 (user_99)  → hash → partition 3
  msg5 (user_42)  → hash → partition 2     ← always here

Same customer goes to the same seat, every time. Deterministic. This is the trick that gives Kafka both per-tenant ordering AND horizontal parallelism: user_42's messages stay strictly ordered (one partition, one consumer reads in offset order), while user_42 and user_99 can be processed by different consumers in parallel.

The dominant pattern for multi-tenant agent systems: key=tenant_id. Per-tenant ordering for free, horizontal scale up to num_partitions consumers per group. This is the load-bearing reason production agent systems pick Kafka over a queue.

Setting the number of partitions

Partitions are set at topic creation time. Two ways:

CLI (most common)

kafka-topics.sh --bootstrap-server localhost:9092 \
  --create \
  --topic research-tasks \
  --partitions 12 \
  --replication-factor 3

--partitions 12 = 12 parallel logs. --replication-factor 3 = each partition copied to 3 brokers for durability (unrelated to parallelism, just safety).

Programmatic (Python AdminClient)

from kafka.admin import KafkaAdminClient, NewTopic

admin = KafkaAdminClient(bootstrap_servers='192.168.1.156:30092')
admin.create_topics([
    NewTopic(name='research-tasks', num_partitions=12, replication_factor=1)
])
The auto-create gotcha. If a producer publishes to a topic that doesn't exist, Kafka auto-creates it using the broker's num.partitions default — typically 1. That's why kafka_agents.py's topics ended up with 1 partition: never explicitly created, the producer's first p.send() auto-created with the broker default. Silent 1× parallelism cap forever. Production discipline: set auto.create.topics.enable=false on the broker and require explicit topic provisioning.
Adding partitions later is painful. You can ADD partitions to an existing topic, but you can never REMOVE them. And adding partitions changes the key→partition mapping (hash(key) % 12 ≠ hash(key) % 24) — so user_42's messages that used to go to partition 7 may suddenly go to partition 19, breaking per-user ordering for in-flight messages. Pick partition count generously up front. 12, 24, 48 are common starting points.

Consumer assignment within a group

Now the parallelism rule snaps into place:

Within a consumer group, each partition is assigned to exactly ONE consumer at a time. Never two. This preserves the per-partition ordering guarantee.

1 consumer in the group → that consumer owns all partitions

Topic with 12 partitions + group 'news-group' has 1 consumer:
  partitions 0-11  →  consumer A   (reads from all 12)

The consumer multiplexes across partitions internally — your for msg in c: loop sees a stream of messages from whichever partition has data ready. You don't see which partition each came from unless you check msg.partition.

Add a second consumer → Kafka triggers a rebalance

Before:
  partitions 0-11  →  consumer A

After adding consumer B (rebalance fires):
  partitions 0-5   →  consumer A
  partitions 6-11  →  consumer B

Add a third → ~4 partitions each. Per-consumer load drops as you scale workers — until you hit the partition count.

More consumers than partitions → excess sit idle

Topic with 4 partitions + group 'news-group' has 6 consumers:
  partition 0  →  consumer A
  partition 1  →  consumer B
  partition 2  →  consumer C
  partition 3  →  consumer D
  consumer E, F  →  IDLE (no partition to claim)

Partitions are the upper bound on consumer parallelism per group. If you anticipate scaling to 8 workers, create the topic with at least 8 partitions up front.

The hot-partition trap

The flip side of deterministic hashing: if 90% of your traffic is from one customer, 90% goes to one partition. That partition's consumer gets overwhelmed while the others sit idle.

  • Mitigation 1: key by a more granular dimension — hash(user_id + conversation_id) instead of just user_id
  • Mitigation 2: for tenant-isolated workloads, run separate topics per tenant
  • Mitigation 3: custom partitioner that detects hot keys and spreads them (rare, complex)

7. Pinning consumers to specific partitions

Default group-managed assignment is fine for general-purpose consumer fleets where workers are interchangeable. But sometimes you want "consumer X always owns partition Y" — for stateful per-tenant agents, GPU-pinned workers, or replay debugging. Three paths, in order of how often they're used:

Path A — assign() instead of subscribe() (manual, deterministic)

from kafka import TopicPartition, KafkaConsumer

def partition_for(key, num_partitions):
    return abs(hash(key)) % num_partitions

target = partition_for('user_42', num_partitions=12)

c = KafkaConsumer(
    bootstrap_servers='...',
    # NOTE: no group_id — going outside consumer groups
    value_deserializer=lambda m: json.loads(m.decode())
)
c.assign([TopicPartition('chat-events', target)])   # claim partition 2

for msg in c:
    # This consumer reads ONLY partition 2.
    # user_42's messages are guaranteed to flow through here.
    handle(msg)
subscribe() (group-managed)assign() (manual)
Partition assignmentKafka coordinator decidesYou decide explicitly
Rebalance on consumer join/leaveYes, automaticNo — assignment is static
group_id neededYesNo (optional)
Offset commitsPer-(group, partition) automaticManual if you want persistence
ScalingAdd/remove consumers, Kafka redistributesYou manage the binding yourself
Use assign() when:
  • Stateful per-tenant agents — "the user_42 chat agent" holds in-memory state, reads only user_42's partition
  • Sharded workers with hardware pinning (worker 0 owns GPU 0 and partition 0)
  • Debugging or replay — point one consumer at one partition and step through
Don't use assign() when:
  • Workers are interchangeable — let the group manage it
  • You want automatic failover — if your assign() consumer dies, no one picks up its partition

Path B — Custom partition_assignment_strategy (group-managed, custom mapping)

If you want group benefits (automatic rebalance, failover, offset coordination) but also want "consumer X always owns partition Y" within the group, write a custom assignor:

from kafka.coordinator.assignors.abstract import AbstractPartitionAssignor

class TenantPinnedAssignor(AbstractPartitionAssignor):
    name = 'tenant-pinned'
    version = 0

    def assign(self, cluster, members):
        # Honor each member's preferred partition list, fall back to even
        # distribution if conflicts. Implementation is fiddly.
        ...

    def metadata(self, topics):
        return ConsumerProtocolMemberMetadata(
            self.version,
            list(topics),
            user_data=encode({'desired_partitions': [2, 5]})
        )

c = KafkaConsumer(
    'chat-events',
    group_id='chat-group',
    partition_assignment_strategy=[TenantPinnedAssignor],
)

Rare in practice. Writing a correct group-aware assignor is hard — it must handle membership churn and produce the same assignment on every member without coordination beyond the coordinator. 95% of real systems use assign() when they need pinning, default assignor when they don't.

Path C — Per-tenant group_id (the "broadcast + filter" pattern)

# Spawn one consumer per tenant, each with its own group_id.
# Each group reads ALL messages on the topic, filters in code.

c = KafkaConsumer(
    'chat-events',
    group_id=f'tenant-{tenant_id}-group',   # unique per tenant
)
for msg in c:
    if msg.key.decode() != tenant_id:
        continue   # filter — drops ~99% of messages at high traffic
    handle(msg)

This is exactly what kafka_agents.py does — three different group_ids, each filters by content. Fine for a 3-message demo, wastes resources at scale because every group reads every message and discards most.

The recommended pattern for production

# 1. Topic 'research-tasks' with N partitions
# 2. Producer keys by routing dimension
p.send(TASKS_TOPIC, key=agent_type.encode(), value=msg)

# 3. One consumer group per agent type
# 4. Within each group, scale workers up to partitions assigned to that type
c = KafkaConsumer(
    TASKS_TOPIC,
    group_id='news-group',
    enable_auto_commit=False,    # manual commit
)

You get per-agent ordering, independent fan-out across agent types, horizontal scaling within each agent type, and real at-least-once delivery — without ever calling assign(). The group_id + key combination handles the pinning cleanly.

Senior takeaway: reach for assign() only when a specific worker truly must be pinned to a specific partition for state-locality reasons. Otherwise, the right answer is "key by tenant + group_id per consumer type" — Kafka does the binding for you and you get failover for free.

8. The Agent-as-Kafka-Consumer pattern

Three roles, each a long-running process:

flowchart TD P[producer process
publishes 3 tasks] -->|research-tasks| T[(broker)] T --> N[news_agent
group_id=news-group
filters task.agent==news] T --> Tech[technical_agent
group_id=technical-group
filters task.agent==technical] T --> E[examples_agent
group_id=examples-group
filters task.agent==examples] N -->|finding| F[(research-findings)] Tech -->|finding| F E -->|finding| F F --> AG[aggregator
group_id=aggregator-group
dedup by agent name
stop after 3]

Why the design is this way

  • Three different group_ids on TASKS_TOPIC → each agent type independently reads all tasks, then filters by content (task['agent'] == agent_type). This is fan-out by content, not by partition.
  • Aggregator on a different topic + its own group_id → independent reader of findings, doesn't compete with anyone.
  • for msg in c is a blocking iterator — it polls the broker and yields each message in turn. This is the agent's main loop. The process runs forever (or until SIGTERM).

The pattern's strength: failure isolation

Kill the news_agent process. The other two keep working. news_agent's offsets stay committed; restart and it picks up where it left off — no data loss, no coordination required. This is the kind of failure-isolation in-process orchestrators can't give you.

9. Kafka vs the alternatives

SystemWhen to pick over KafkaTradeoff
LangGraph / CrewAI in-process Single request, single process, no replay needed No durability, no horizontal scale, no audit log
Redis Streams Lightweight, already running Redis, <1M msgs/day Smaller ecosystem, weaker partitioning, no exactly-once
SQS / Cloud Pub/Sub You want managed, don't want to operate Kafka SQS has no replay; Pub/Sub costs more at scale
Celery + RabbitMQ Task queue semantics dominate; Python-native Messages disappear when ack'd — no replay; harder to fan-out
Temporal Long-running stateful workflows with retries, sleeps, signals Different mental model — workflow durability vs event log
The senior framing: Kafka is not a queue. It's a durable, replay-able commit log. Pick it when you need replay, multi-consumer fan-out, audit, or partitioned parallelism. Pick a queue (SQS, Celery) when you only need task dispatch and the message has zero value after it's processed.

10. Production gotchas

Rebalance storms

When a consumer in a group joins or leaves, Kafka triggers a rebalance — partition assignments shuffle across the surviving group members. During rebalance, no consumer in the group is reading. If your consumers crash often (OOM, deploy, scaling event), rebalances cascade. Mitigation: session_timeout_ms, heartbeat_interval_ms, sticky-partition assignor.

Hot partitions

If one user generates 90% of traffic and you key by user_id, one partition becomes a hotspot while others sit idle. Pick a key with high cardinality, or hash by (user_id, sub_id) to spread one user's traffic across multiple partitions at the cost of order within that user.

Schema evolution

Messages live in the log for the retention period. The consumer that reads tomorrow's messages may also need to read last week's messages. Use Schema Registry (Avro/Protobuf) or Pydantic with backward-compatible field defaults. Never make a non-nullable field required without a migration plan.

Dead-letter queue (DLQ)

What happens when a message can't be processed (malformed JSON, LLM keeps failing)? Without a DLQ, the consumer retries forever and blocks the partition. Production pattern: after N failed retries, publish the bad message to a $topic.dlq topic and commit the offset. A separate human-driven process inspects the DLQ.

Idempotence keys

At-least-once delivery means duplicates happen. If your agent makes an LLM call costing $0.30 and downstream writes to a DB, deduplicate by a stable key (message offset, deterministic task_id) before doing the expensive work. Otherwise budget for 10–20% duplicate spend on bursty workloads.

Auto-commit vs at-least-once mismatch

The kafka_agents.py in this repo uses default enable_auto_commit=True — fine for a demo, wrong for production. The auto-commit timer can advance the offset before the LLM call and finding publish complete. Production: disable auto-commit, call c.commit() after each finding is successfully published.

Auto-create-topics silent scale ceiling

If a producer publishes to a topic that doesn't exist, Kafka auto-creates it with the broker's num.partitions default — typically 1. The system works fine for months, then can't scale because adding more consumers to the group does nothing past the first one. Fix: set auto.create.topics.enable=false on the broker and provision topics explicitly with the partition count your future scale will need.

11. Interview answer — the 90-second version

"Kafka is a durable, partitioned commit log — not a queue. The mental model is five primitives: brokers store topics, topics are actually N parallel partitions, producers append messages, consumers track their position via offsets keyed by group_id. The single most important concept is group_id: same group_id across N consumers gives you load-balanced queue semantics — each partition assigned to exactly one consumer, so partition count is the upper bound on parallelism. Different group_ids give you broadcast pub-sub. Ordering is guaranteed within a partition, not across — so you key by whatever needs strict order, typically tenant_id for multi-tenant agents, which gives you per-tenant ordering and horizontal parallelism in the same primitive. Offsets are committed to mark progress; default is at-least-once, but only if you commit correctly — the auto-commit timer is a silent at-most-once trap because it can commit before your processing finishes. Production discipline: disable auto-commit, call commit() after the side effect, design idempotent processors. For agent systems, the killer feature is replay: spin up a new group_id with auto_offset_reset='earliest' and you re-process every input under a new prompt version with zero data movement. When you need a specific worker pinned to a specific partition for state-locality reasons — stateful per-tenant agents, GPU-pinned workers — reach for assign() instead of subscribe(); otherwise the group_id+key combination handles binding cleanly. The pattern I built in P3 — Agent-as-Kafka-Consumer — has three long-running consumers each on a different group_id reading the same research-tasks topic and filtering by content, then publishing findings to a second topic the aggregator consumes. Production gotchas to know: rebalance storms, hot partitions, schema evolution, dead-letter queues, auto-commit trap, and the auto-create-topics-with-1-partition silent scale ceiling."
