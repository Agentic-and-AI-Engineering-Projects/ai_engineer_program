AWS Services Reference for AI Engineers

Quick-reference catalog of 140+ AWS services, organized by category. Drawn from Rajesh's AWS Solutions Architect Associate prep notes. Each entry distills the service's key behavior in one or two lines — not a tutorial, a working catalog you can scan when an interviewer says "what would you use for X?"

How to use this appendix: Don't read top to bottom. Pick a category from the nav, scan the table, find the service. The point is to recognize service names and know roughly what they do — depth comes from hands-on use. For AI engineering specifically, the categories that matter most are Compute (where your inference runs), Storage (S3 for model artifacts, EFS for shared files), Networking (VPC for private model endpoints), Security (KMS, Secrets, IAM), and ML/AI services (Bedrock has its own Appendix L).

Services an AI Engineer touches most

If you only have time to drill into a handful, prioritize these (in addition to Bedrock — see Appendix L):

ServiceWhy it matters for AI work
S3Where every model artifact, training dataset, RAG corpus, prompt template, evaluation gold set, and observability log eventually lands. Production AI runs on S3 underneath.
LambdaCheap event-driven glue for AI pipelines — trigger an ingest when a PDF lands in S3, run a small classification call, dispatch to Step Functions. Pair with API Gateway for serverless inference endpoints.
EC2 + Auto ScalingFor workloads too heavy for Lambda — long-running agents, GPU inference, embedding generation at scale. Auto Scaling matches capacity to traffic.
EKSManaged Kubernetes for production AI deployments. See Appendix M.
IAM + KMS + Secrets ManagerThe non-negotiable security trio. IAM controls who/what can call your models. KMS encrypts model weights and embeddings at rest. Secrets Manager holds API keys (Anthropic, OpenAI, vector DBs) for application access.
VPC + VPC EndpointsPrivate network for sensitive workloads — keep traffic between your app, Bedrock, and S3 entirely inside AWS without touching the public internet.
API GatewayFront door for AI service APIs you expose externally. Authentication, rate limiting, request validation.
SQS / SNS / EventBridgeAsync message buses for agent task queues, evaluation pipelines, drift-alert routing. SQS for queues, SNS for fan-out, EventBridge for cross-service routing on event schemas.
CloudWatch + CloudTrailLogs and metrics (CloudWatch) + audit trail of every API call (CloudTrail). Production observability and compliance.
Step FunctionsState-machine orchestration for multi-step pipelines — ingest → embed → store → notify. Lower-level alternative to LangGraph when AWS-native is preferred.
OpenSearch (not in this list but worth knowing)Managed Elasticsearch with vector-search capabilities. AWS's answer to running Qdrant/Pinecone-style vector workloads with full Elasticsearch text + filter capabilities.
DynamoDBServerless NoSQL for low-latency lookups — feature stores, session state, cache layers for agent memory.
RDS / AuroraManaged Postgres / MySQL. Aurora Serverless v2 auto-scales for spiky workloads. Used for application data and (with pgvector extension) as a vector store at smaller scales.
ElastiCacheRedis or Memcached managed. Use cases: prompt caching, embedding cache, rate-limit counters, agent session state.

The 60-second interview framing

"My AWS framing for AI workloads is: data lives in S3, compute that's bursty or event-driven lives in Lambda, compute that's heavy or stateful lives in EC2 or EKS, vector workloads go to Pinecone or Bedrock-managed retrieval at smaller scales — Aurora pgvector or OpenSearch when I want to keep everything inside AWS. Cross-service flow uses SQS for queues, SNS for fan-out, EventBridge for schema-routed events, Step Functions for ordered orchestration. Security is the boring baseline: IAM least-privilege, KMS for encryption at rest, Secrets Manager for credentials, VPC endpoints so my Bedrock and S3 calls never leave the private network. Observability is CloudWatch + CloudTrail. The most important architectural insight isn't which service to pick — it's that AWS's surface area is huge, so the discipline is constraining yourself to a small set of well-understood primitives and resisting service sprawl."
